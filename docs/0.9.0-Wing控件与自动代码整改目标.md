# 0.9.0 Wing 控件与自动代码整改目标

状态：current

Owner：KT Auto Code / Phoenix Wing maintainers

适用版本：KT Auto Code 0.9.0、Phoenix Wing 0.7.3 开发线

最后核验：2026-09-08

## 本轮目标

1. 将本仓 `PnwCombo` 的可管理条目能力迁入 Phoenix Wing，保留分组、逐行删除、全部清空、键盘操作、视口定位和上下自动避让；KT Auto Code 改为消费 Wing 导出，不保留两套实现。Wing 阶段提交：`2b647d6`。
2. 在 Wing 提供 Host-neutral 的统一清理对话框，以及可由 Node Host 复用的预览、冻结、复验和执行能力。Wing 阶段提交：`2b647d6`。
3. AutoBuild Primary 的“执行”按钮组增加 **清理**；点击后打开统一对话框。Primary 维护区不再常驻“清理仓库”和“手动清理 Root”两个块。
4. 清理范围覆盖 **ROOT_DIR** 与 **工作目录**；清理模式覆盖 YAML 规则清理、CMake 构建目录清理，以及显式高风险的 `git reset --hard + git clean -ffdx`。
5. 完成“自动代码”原型与正式 UI / 真实交互的一轮整改。任何原有按钮或能力若未明确要求删除，必须保留、迁移或登记为待接入，禁止静默消失。
6. 梳理 Git Primary 的空状态和仓库管理按钮；移除与 VS Code 原生能力重复的“新建 Git 仓库”，保留插件独有的递归发现、仓库切换、刷新和已登记仓库管理能力。
7. 点检集成 Toolbar 中竖向 `CODE` rail 的框架语义；若 Phoenix Wing Ribbon 已有分组折叠能力，则让该 rail 成为可访问的折叠/展开触发区并复用同一状态，不新增与现有 Toolbar chevron 冲突的第二套状态。
8. 扩展 AutoBuild 的 `BUILD_MANIFEST.json` 使用链路：允许把清单中的 Git 地址先导入为构建草稿，
   不要求目标仓库已存在；后续统一执行时对缺失目录执行检出，对已存在仓库执行更新，并继续进入依赖它的
   link / export / build 节点。

锁定的三段式 Primary 外壳（Toolbar、目录、Current Tool）不在本轮变更范围内。

## 统一清理对话框约束

- 组件只接收 Host 投影并发送语义事件，不直接读取 VS Code API、配置文件或工作区状态。
- 必须显示目标类型、绝对路径、规则/动作摘要、预计命中数量和精确预览；危险等级不能只靠颜色表达。
- YAML 规则清理默认只处理目标目录的直接子项；目录树快照不跟随符号链接，确认后只删除冻结且复验一致的目标。
- Git 强制清理必须单独标为高风险，明确展示 `git reset --hard HEAD` 与 `git clean -ffdx`，不可借普通“清理”确认静默执行。
- 工作目录和 ROOT_DIR 必须分别投影；路径缺失、文件系统根、不可访问路径和确认后身份变化一律拒绝执行。
- 组件可被 AutoBuild、Run 和其他插件复用；业务配置保存、Output 日志和生命周期取消由 Host 负责。

## AutoBuild PowerShell → TypeScript 边界

子 agent 已完成只读审计。当前决定如下：

### 本轮保留 PowerShell

- 项目自带 `mk.ps1`、`export.ps1` 和 Root 下发的 `linkCAA.ps1`：其中可能有项目专属前后处理。
- CAA/MSVC 的实际构建 runner；调度可迁移 TS，底层 Windows 工具链暂不改写。
- “构建脚本”和“仓库检出”的保存/导出继续生成 Windows PowerShell 5.1；本轮不新增 `.sh`。
- `Invoke-AutoBuild.ps1`、`Functions-Cleanup.ps1` 与 sample 继续作为独立部署、示例和回退工具，
  但插件运行时可逐步不再依赖这些脚本。
- “版本归档”是 JSON，不归入脚本平台限制。

### 可迁移到 TS / Wing

| 能力 | 归属 |
| --- | --- |
| 配置校验、路径规范化、任务选择与 DAG / 失败跳过状态 | Wing `run-core` |
| Git 探测、更新和强制清理；目录探测、复制、hash、进程执行、流式日志 | Wing `run-node` |
| Root / 工作目录规则清理和 CMake 产物清理 | Wing `run-core` 规则 + `run-node` 执行 |
| 统一清理弹窗与 preview token / 高风险确认 | Wing UI |
| VS Code 弹窗、OutputChannel、Task、workspaceState | KT Auto Code Host adapter |
| AutoBuild 配置到具体任务的业务映射、ROOT/tools 同步布局 | KT Auto Code 产品层 |

### “运行”失败继续规则

1. TS 校验、目录解析和项目探测始终执行；每个 Git 仓库独立产生结果。
2. ROOT / 3rdParty 失败时跳过依赖它们的 link/export/build；普通项目 Git 失败只跳过该项目链。
3. `linkCAA.ps1` 或某项目 `export.ps1` 失败，只跳过其依赖项目；其他项目继续。
4. CMake 项目可独立并行；保持当前正式语义：任一 CMake 失败，本轮全部 CAA 标为“已跳过”，
   待建立项目级依赖后再缩小范围。
5. CAA 项目失败不影响其他已就绪 CAA 项目。
6. PowerShell 不存在或无法启动时，PS 节点标为“不可用 / 已跳过”；TS 探测、Git 状态刷新、
   汇总和日志继续。不得因此自动触发清理或脚本同步。
7. 用户停止后不再创建新任务，终止运行中的 PS；未启动项标为“已取消”，不是“失败”。
8. 错误以进程启动失败或退出码判定，不能按 stderr 是否有文本判定。

正式状态模型还需增加 `skipped / cancelled` 和依赖关系；当前单体
`Invoke-AutoBuild.ps1 -SkipBuild` 失败即中断的路径在新 DAG 就绪前继续保留，不能先删回退链。

### 原有执行能力保留表

- 配置：打开、保存、另存、关闭、详细配置、最近配置。
- 执行：脚本、预检配置、启动、停止、并行编译、Output、新增统一清理。
- Right：预检、运行/停止、ROOT / 3rdParty 更新选择。
- 项目表：选择目录、探测当前目录、移除未启用项、探测列，以及逐项目启用、分支、更新、
  CMake、CAA、linkCAA、探测、运行、移除。
- 任务行单步运行；脚本对话框三个页签和目标目录选项；ROOT/tools 与 ROOT/sample 同步。

### `BUILD_MANIFEST.json` 导入与检出 / 更新

- 现有 schema v1 继续代表一次成功构建后的版本归档；`finishedAt`、`status`、完整 Commit 和
  `dirty` 是当时事实，导入后不能当成当前探测结果。
- “项目与仓库”Header 增加短按钮 **导入…**；系统文件选择器接受清单后，仅显示“新增 / 更新 /
  忽略”的简短汇总并由用户确认合入草稿。正常情况不显示明细表；只有 Origin 冲突、目标重名或
  格式错误才展开问题项。导入不访问 Git、不要求目标目录存在，也不直接检出、更新或构建。
- 仓库以规范化 Origin 去重。`root`、`thirdParty` 分别映射到 ROOT_DIR、ROOT_DIR_3rdParty；
  `project` 映射为项目表行，保留 branch、commit 和 buildKinds。
- schema v1 没有目标相对目录：普通项目默认建议为 `工作目录/<name>`，必须在导入预览中明确显示，
  并允许用户在执行前修改。不得仅凭当前机器上恰好存在的同名目录静默绑定。
- 统一执行前逐条探测：目标目录不存在时计划为“检出”，存在且是同 Origin Git 仓库时计划为“更新”，
  存在但不是 Git 仓库、Origin 不一致或目标路径冲突时停止该仓库并要求处理；其他独立仓库继续。
- 指定完整 Commit 时先 clone/fetch，再检出该 Commit；未固定 Commit 时按 branch 检出或
  `pull --ff-only`。Root / 3rdParty 继续执行 LFS 与递归子模块步骤。
- 这项先登记为 AutoBuild 后续阶段；正式 UI、消息契约和真实执行未完成前，不把它标为已支持。

只有替代能力、测试与真实 Host 验收完整后，才可删除 Primary 旧常驻清理块、隐藏代理 substrate、
无调用者的旧 `exportLauncher` 和过期 `clean` 字段。Primary/Right 双入口、单项目/单任务运行、
脚本同步/脚本导出、Git untracked/强制恢复、JSON 归档/脚本导出均不是重复能力。

## 验收与归档

- 原型先体现最终按钮位置、弹窗层级、状态和日志，再映射正式 UI。
- 每个迁移项必须有单元测试；弹层必须有真实浏览器的深色、浅色、高对比和窄 Primary 点检。
- KT Auto Code 使用并列 Wing 的 `pnpm ext:dev:prepare` 通过后，才可声明本地集成通过。
- 两个仓库分别阶段提交；不改版本、不发布、不推送，除非用户另行明确要求。
- 位于 `Phoenix/worktrees/<repo>` 的消费者先建立 `worktrees/phoenix-wing` 到明确活动 Wing 检出的
  仓外符号链接；规则已写入 `AGENTS.md` 与《本地 Wing 并列开发》，链接不进入 Git 或发布制品。
