## 2. 已确认目标 Shell：两个一级区域

```text
KT Auto Code                            [目录显隐] [忽略] [设置]
├─ 目录 Row（默认显示，可由 Header 隐藏）：固定一行，表达共享目录
└─ 工具区域
   ├─ Toolbar Strip：`箭头 + Ribbon + …` 共用一层；无独立标题行
   └─ Tool Surface：无独立 Header 行
      ├─ 右上角：不占行、可键盘到达的悬浮 `×`
      └─ 内容：操作、状态和结果；独立滚动
```

用户已明确同意以该层级替换旧的并列一级区域，并在后续明确确认移除整行 Sub Tool Header。Webview 只有“可显隐目录 Row”和“工具区域”两个一级槽位；Toolbar Strip 与 Tool Surface 都属于工具区域内部。当前工具内容仍是**二级功能区**，但不再通过重复标题行表达层级：活动 Ribbon/Group、弱分隔和 Surface 自身内容共同提供上下文。

### 2.1 原生 Header 与目录 Row

- 原生 View Header 固定依次放“目录显隐、Ignore、Settings”，不放搜索放大镜、目录齿轮或 Webview 内部 Ignore 快捷方式。
- 当前三项是 Header 已确认的最小核心集；以后可以少量增加真正全局且高频的图标，但必须显式评审、同步契约与测试，普通工具按钮继续留在 Toolbar/Tool Surface。
- 目录 Row 是 Webview 第一个一级槽位；显示时位于 Primary 内容顶部并固定一行，隐藏时不保留空白占位。
- 首次使用或尚无持久化偏好时默认显示。之后保存用户的显隐偏好；重载 View / Extension Host 后按偏好恢复。
- Header 的目录动作在显示态使用 `folder-opened`，Tooltip 为“隐藏目录”；隐藏态使用 `folder`，Tooltip 为“显示目录”。
- 隐藏只是视图选择：不得清空、回退或重新推导已选目录、最近目录、外部目录标识及工具正在使用的目录上下文。
- 只表达共享工作目录；不放工具标题、MRU、任务状态或操作按钮。
- 目录路径占用剩余宽度，完整值保留在 Tooltip 和 `aria-label`。
- 行内保留实际目录选择入口，不再用左侧装饰性文件夹；它与 Header 的“目录 Row 显隐”不是同一动作。
- 目录 Row 当前的位置、单行结构、目录文字、下拉、右侧选择入口以及显示/隐藏行为已获用户观感确认，作为后续改动不得偶然破坏的基线。

### 2.2 Toolbar Strip

- 箭头、Ribbon 和唯一 `…` 在同一行，不再为“工具栏”额外浪费一行标题。
- 展开态保留现在的图标+文字 Ribbon；紧凑态只显示图标。
- Toolbar 箭头只改变 Ribbon 的展开/紧凑形态，不隐藏目录 Row 或 Tool Surface，不销毁工具状态。
- 展开与紧凑必须复用同一个 Ribbon DOM；`…` 仍是 Ribbon 定制的唯一入口。
- 现有展开/紧凑效果已获用户确认并作为本轮固定基线；更多二级菜单如何迁入统一直接叶子模型留作后续研究，不继续扩大本次阶段归档。

### 2.3 Tool Surface

- 只容纳当前一个逻辑工具，不堆叠多个并列业务 Block。
- 视觉上使用比一级 Block 更轻的二级层级：直接跟随 Ribbon、弱分隔、满宽内容，不复制粗重外壳或整行标题 Header。
- 重复点击当前 Ribbon Tool/Group 只收起或展开 Surface；逻辑工具仍打开且保持当前项，MRU、Editor、后台任务、草稿、结果和每个工具的滚动缓存不变。
- 选择其他 Ribbon 工具，或从 `…`、命令、原生 Header、Editor 激活工具时，Surface 必须展开；外部激活不能留下“工具已打开但内容仍不可见”的状态。
- `×` 以右上角悬浮按钮存在，不占独立行，必须键盘可达并有 Tooltip/`aria-label`。它只关闭左侧逻辑工具，不隐式关闭 Editor、取消任务或清空结果。
- `×` 关闭后按同一个 MRU 栈恢复上一个逻辑工具；最后一个关闭后显示欢迎态。Editor、后台扫描/进程、草稿和结果仍按各自生命周期保留。
- Primary 页面和工具区域本身不做日常纵向滚动；只有 Tool Surface 内容是唯一滚动边界。

```text
目录显示 + Ribbon 展开
原生 Header                                  [folder-opened] [忽略] [设置]
├─ 目录 [当前目录………………………………………… ▾] [选择目录]
└─ 工具区域
   ├─ ⌄ [代码辅助] [Git] [Run] [搜索替换]              […]
   └─ [搜索] [替换] [项目改名]                    [×]
      状态与结果（Tool Surface 内滚动）

目录隐藏 + Ribbon 紧凑 + Tool Surface 收起
原生 Header                                         [folder] [忽略] [设置]
└─ 工具区域
   └─ › [当前图标] [图标] [图标] [图标]                  […]
          再次点击当前图标恢复 Tool Surface
```

## 3. 一级/二级入口是同一种工具

“一级”和“二级”只表示按钮放在哪个导航位置，不表示两种不同的 Primary View：

- Ribbon 上的“搜索替换”和功能菜单里的“头文件引用修正”都是普通 `toolId`。
- Ribbon、菜单、命令和 Editor 只能把已注册的直接叶子 `toolId` 交给统一激活通道，并在同一 Tool Surface 中渲染；聚合目录 ID 不得代替叶子执行。
- 工具的状态、MRU、Surface 显隐、关闭、草稿恢复和权限判断不因入口层级而分叉。
- “功能目录”只是为不常用工具提供更深导航；它不创建另一套二级工具运行时。

建议统一描述：

```ts
interface KtcToolDescriptor {
  readonly id: string;
  readonly title: string;
  readonly entry: {
    readonly ribbon?: { readonly order: number };
    readonly menu?: { readonly group: string; readonly order: number };
  };
}

interface KtcToolActivation {
  readonly toolId: string;
  readonly source: "ribbon" | "menu" | "editor" | "command";
  readonly preserveFocus?: boolean;
}
```

`source` 只用于焦点和诊断，不决定工具类型。系统始终通过 `toolId` 选择当前 Tool Surface。

## 4. 简单工具与复杂工具的统一分工

| 工具形态 | Primary Tool Surface | 右侧 Editor View |
| --- | --- | --- |
| 简单工具 | 表单、操作、状态和短结果全部保留 | 不需要 |
| 复杂工具 | 当前任务摘要、计数、阶段状态、少量高频动作、“回到 View” | 完整表单、配置、长列表、规则、详细结果和日志 |

同一复杂工具仍只有一个领域 Controller 和一份真实状态。Primary 与 Editor 只是两个投影，不得互相模拟 DOM 点击，也不得各自保存一份可执行草稿。

## 5. Editor companion 契约

```ts
interface KtcEditorPrimaryContribution {
  readonly panelId: string;
  readonly toolId: "projectRename" | "autoBuild";
  readonly sessionId: string;
  readonly revision: number;
  readonly lifecycle: "active" | "visible" | "open-inactive" | "disposed";
  readonly title: string;
  readonly ready: boolean;
  readonly status: "idle" | "running" | "done" | "error";
  readonly message: string;
  readonly summary: readonly { label: string; value: string }[];
  readonly actions: readonly {
    id: string;
    label: string;
    enabled: boolean;
    tone?: "primary" | "secondary" | "danger";
    disabledReason?: string;
  }[];
}
```

Extension Host coordinator 保存快照并把它投影到当前 Tool Surface。Primary 发送 `panelId + toolId + sessionId + revision + actionId`；文件系统、进程、报告和写盘继续由 Controller/Host 负责。

### 5.1 激活与焦点

1. Ribbon、二级菜单、命令面板和 Editor 的直接叶子激活都进入同一 `activateTool` 通道；`source` 只影响焦点保持和诊断。
2. Editor `active=true` 时使对应工具成为当前 Tool Surface，但用 preserve-focus 路径保持焦点在 Editor。
3. 用户点击 Primary 后 Editor 会暂时变为 inactive：仍在分栏中可见则标记 `visible`，被其他 Tab 遮住才标记 `open-inactive`；两者都不立即切回旧工具。
4. 分栏同时可见多个 Editor 时，以最近一次 `active=true` 的 Panel 为准。
5. Panel dispose 后将路由标记为 `disposed` 并停止转发；可以保留拒绝迟到消息所需的最小 tombstone，但旧 session 不再可执行。
6. 用户手工隐藏侧栏后，Editor 切换只更新 Host 状态，不反复强制打开 Primary。

### 5.2 草稿与危险动作

自动编译的未保存配置和项目改名的“表单已修改 / 报告已失效”仍有 Editor DOM 状态。Primary 不能使用旧 `workspaceState` 或上一次摘要直接执行。

需要最新草稿的动作统一使用握手：

```text
Primary 点击
  → Host 校验 toolId / sessionId
  → Editor 返回 draftRevision / reportId / 完整表单
  → Host 再次校验 session 和 revision
  → 进入既有 Controller 门禁
```

Editor 未 ready、已关闭、请求超时、revision 过期或报告漂移时都不执行。

## 6. 两个原型验证对象

| 工具 | Primary Tool Surface 原型 | Editor 继续保留 |
| --- | --- | --- |
| 项目改名 | 绑定目录、`Source → Target`、规则/命中/风险数、阶段状态；首先接“回到 View、取消、Git 对比” | 名称和前缀输入、历史、档案、规则、候选、命中与风险列表、Diff、写盘门禁 |

首阶段只镜像不依赖草稿的安全动作，并保留 Editor 原按钮，避免用户隐藏 Primary 后无法完成任务。握手稳定后才候选迁移“分析 / 启动 / 预览 Diff / 执行改名”。

## 7. 已知实施风险

- 用户已明确确认把旧的并列一级布局迁移为“两区 Shell + 无 Header Tool Surface”，并确认重复点击当前 Ribbon Tool/Group 控制 Surface 显隐、悬浮 `×` 单独承担逻辑关闭。`AGENTS.md` 与 UI 权威规则随第二轮原型同步更新；主题、窄宽、重载和 Windows CAA 实跑仍按清单继续覆盖。
- 改变 DOM 层级会影响边框、Tab 顺序、焦点恢复、折叠状态、MRU 与唯一滚动区，必须作为独立 Shell 步骤验证。
- 原生 Header 新增目录显隐状态，会引入首次默认值、持久化、图标/Tooltip 同步和隐藏不丢上下文四条回归边界；不得用重建默认目录来实现“显示”。
- Auto Build 手工添加目前没有真正以 Git top-level 作为项目身份，同一仓库的根目录/子目录可能重复。这是独立功能缺陷，记入 TODO，不与 Shell 原型混成一个修改。
- 项目改名写盘中需禁止新任务替换旧 session，防止迟到结果覆盖新状态。原型不降低该安全门禁。
- 现有功能目录仍有可继续迁移的二级入口。后续研究应逐项确认入口身份、状态所有权和 Primary/Editor 分工；本轮只证明统一直接叶子通道可行，不批量搬迁剩余菜单。

## 9. 自动测试计划

- DOM 一级区域严格只有可显隐目录 Row 和 Tool Area；Tool Area 内 Toolbar 在 Tool Surface 之前。目录隐藏后不得出现空白占位或把内部子级提升为一级。
- 原生 Header 的可见动作顺序为目录显隐、Ignore、Settings；目录图标与 Tooltip 对应当前状态，首次默认显示且偏好可恢复。
- 隐藏目录 Row 前后，选中目录、最近目录、外部目录标识和下游工具有效上下文保持不变。
- Toolbar 紧凑/展开不影响 Tool Surface；重复当前 Ribbon 项收起 Surface 不影响 Ribbon、MRU 或工具任务状态。
- 目录、Toolbar、Tool Surface 内容与悬浮关闭的 Tab 顺序可预测；不存在空的 Header 焦点位。
- Ribbon、二级菜单、命令和 Editor 的同一直接叶子 `toolId` 产生完全相同的当前工具、MRU、草稿恢复和 `×` 行为。
- Editor active/inactive/visible/disposed 与双分栏最近激活归约有纯状态测试。
- Primary 每条 companion 动作都校验 `toolId/sessionId/actionId/ready`；迟到消息不能作用于新任务。
- 项目改名执行仍经过冻结报告和漂移复验；编译不从旧 `workspaceState` 启动。
- 280 / 360 / 560 / 760px 宽度下无水平页面滚动，目录选择、当前 Ribbon 项和悬浮 `×` 始终可达且互不遮挡。

### 9.1 自动门禁执行顺序

1. 先运行 companion 状态模型、项目改名 Controller、自动编译 Controller、Primary Provider 和 HTML 契约的定向测试。
2. 再运行 `pnpm typecheck` 与 `pnpm test`，确保简单 Primary 工具和既有 Editor View 没有回归。
3. 运行 `pnpm docs:check`，确认本文、索引和生成清单一致且当前文档链接有效。
4. 用 `pnpm ext:dev:code` 启动未安装模式的 Code Extension Development Host 做界面点检；最终本地 Wing 集成声明必须以 `pnpm ext:dev:prepare` 成功为准。
5. 每次门禁记录命令、退出码和通过/失败摘要即可；不得把本机绝对路径、完整命令环境、项目源文件内容或私有配置写入归档证据。

## 13. Tool Navigator：导航层级与二级区域

本节定义 Tool Surface 内部的框架级导航控件，不修改外层两区 Shell 契约。后续不再用“一级/二级 Block”同时指模块、入口、列表和业务内容，而使用稳定名词：

```text
Navigation Tree
└─ Group（role: module）             Code / CAD / 后续模块
   └─ Group（role: tool-group）      代码辅助 / Git / Run / 替换 / 自动代码
      └─ Group（role: category）     C++ 整理 / 文件工具 / CAA（可选）
         └─ Tool（叶子）             编译工具 / 头文件修正 / 编码修正 / UUID …

Tool Registry（不进入 Tree）
└─ toolId → descriptor + Action Map + Controller + 可选 Editor companion
```

- `C++ 整理`、`文件工具`、`CAA` 等只作为 Tool Navigator 内的视觉分类，不拥有任务状态，也不再计作一个导航级别。
- Ribbon 表达 Tool Group，活动项类似 Tab；点击时发出 `selectGroup(groupId)` 导航信号。Group ID 绝不能代替具体 `toolId` 执行业务动作；只有配置了有效 `defaultToolId` 时，Host 才可在选组后显式追加 `activateTool(defaultToolId)`，不得偷偷取第一个子项。
- Ribbon 下方区域命名为 **Tool Navigator**。它用同一份 Tool 描述数据支持“大纲 / 网格”两种表现；切换只改变布局，不改变选择、MRU、任务、权限或 Controller。大纲保持单列层级，网格才根据控件宽度响应为一列或多列，禁止把真正的层级 Tree 横向拆列。
- 只有 Tool 叶子拥有 `toolId`、运行状态和 Primary/Editor 分工。分析、修正、启动、停止等是 Tool 内 Action，不继续增加导航层级。
- 只有一个 Tool 的 Group 仍使用相同数据模型，可自动进入默认 Tool，避免为了形式强制显示一项空导航。

目标运行时统一为：

```ts
interface KtcToolDescriptor {
  readonly moduleId: string;
  readonly groupId: string;
  readonly toolId: string;
  readonly presentation: "primary" | "editor" | "hybrid";
}

interface KtcToolActionDefinition {
  readonly actionId: string;
  readonly label: string;
  readonly placement: readonly ("primary" | "editor")[];
  readonly risk: "read" | "write" | "process" | "destructive";
}

interface KtcToolActionState {
  readonly toolId: string;
  readonly actionId: string;
  readonly enabled: boolean;
  readonly revision?: number;
}

interface KtcToolRegistration {
  readonly descriptor: KtcToolDescriptor;
  readonly actions: Readonly<Record<string, KtcToolActionDefinition>>;
  readonly controller: KtcToolController;
}
```

导航入口只有两种语义：Group 入口提交 `groupId` 选择导航上下文，Tool 入口提交叶子 `toolId` 激活工具。Ribbon 通常选择 Group；树形、图标、`…`、命令与 Editor 可以直接激活 Tool。Primary 统一管理 Group 选择、Tool 激活、可见性、MRU、状态摘要和 Action 路由。工具自行提供内容、Action Controller 以及可选 Editor companion。Action 的外壳可以统一，但写盘、编译、删除等领域校验仍必须由工具 Controller 执行。

Action 不进入导航 Tree，也不作为 Tree 的第三种节点。每个 Tool 在 TypeScript Registry 中维护一份以 `actionId` 为键的静态 Action Map，声明名称、Primary/Editor 投影位置与风险类型；Host 合并各 Tool 的 Map，建立只读全局索引并用 `(toolId, actionId)` 统一寻址和校验。运行时 `enabled`、revision、冻结报告及 handler 仍由所属 Tool Controller 提供，不能写进导航 JSON。Shell 的 `activate / collapse / close / reveal` 使用独立的系统 Action 命名空间，与 `analyze / apply / stop` 等业务 Action 分开注册，避免同名动作跨工具串线或绕过领域门禁。

导航采用“配置描述、代码实现”的双注册方式：

```json
{
  "schemaVersion": 1,
  "nodes": [{
    "kind": "group",
    "role": "module",
    "id": "code",
    "title": "Code",
    "children": [{
      "kind": "group",
      "role": "tool-group",
      "id": "codeAssistant",
      "title": "代码辅助",
      "children": [{
        "kind": "group",
        "role": "category",
        "id": "cpp",
        "title": "C++ 整理",
        "children": [
          { "kind": "tool", "toolId": "autoBuild" },
          { "kind": "tool", "toolId": "headerIncludeFix" }
        ]
      }]
    }]
  }]
}
```

- 模块随包 Manifest JSON 记录完整层级、标题、图标、顺序、默认叶子和允许的 Navigator 展示方式，不包含 Tool 的 Primary/Editor `presentation`、函数或任意可执行脚本。
- 用户布局状态只记录大纲/网格、固定、排序和展开偏好，并引用稳定 ID；不得复制或改写能力树。
- TypeScript Registry 按 `toolId` 注册 Controller（提供运行态与 Action handler）、ViewModel 与可选 Editor companion。Host 合并两者后，缺实现的叶子禁用并输出诊断，不允许从 JSON 动态执行代码。
- 导航节点使用递归可判别联合：Module / Tool Group / Category 在结构上都是 `kind: "group"`，只以 `role` 区分模块所有权、展示层级和默认样式；Group 只导航，不能声明可执行 `toolId`。Tool 叶子不能再有 `children`。Group 可声明 `defaultToolId`，但目标必须是自身后代叶子。
- 同一个递归遍历器负责规范化、排序、折叠以及大纲/网格 ViewModel；UI 默认最多展示 Module → Tool Group → Category 三层 Group，更深配置必须被校验拒绝或显式降级，避免形成不可理解的深树。
- 纯模型单元测试至少拒绝循环、重复 ID、跨 Module 冲突、父节点可执行、叶子带子项、未注册 `toolId`、非法默认叶子和重复 Action ID；树形与图标渲染必须从同一规范化结果产生。

```ts
type KtcNavigationNodeKind = "group" | "tool";
type KtcNavigationGroupRole = "module" | "tool-group" | "category";
type KtcToolPresentation = "primary" | "editor" | "hybrid";
type KtcToolNavigatorMode = "outline" | "grid";

type KtcNavigationNode =
  | {
      readonly kind: "group";
      readonly role: KtcNavigationGroupRole;
      readonly id: string;
      readonly children: readonly KtcNavigationNode[];
      readonly defaultToolId?: string;
    }
  | {
      readonly kind: "tool";
      readonly toolId: string;
    };
```

导航 JSON Schema 只约束 `kind`、Group `role`、层级与 Tool 引用；`presentation` 由 TypeScript Tool Registry 的 `KtcToolDescriptor` 枚举约束，避免 Manifest 与实现各存一份后漂移。`outline | grid` 是用户级显示偏好，不写回能力树。校验器还要限制 Module 只出现在顶层、Tool Group 属于 Module、Category 不跨模块，并为未来新增枚举值要求 schemaVersion 升级或兼容分支。

0.9.0 的首个原型已具备直接叶子激活、MRU、统一 Primary 投影、可选 companion 和 session/revision 动作校验；尚未完全泛化的部分包括 companion 工具 ID 的显式集合、Code Assistant/CAD 的兼容分支及若干工具专用 Webview 消息。下一阶段应先收敛这些模型边界，不把大纲/网格切换变成第三套运行时。

迁移完成后，`codeAssistant` 只是一条普通 Tool Group 配置；通用 Tool Navigator 自动渲染其分类和叶子，删除专用 Tree DOM、feature 状态和消息分支。Code、CAD 与后续模块使用同一 schema，只提供各自配置与 Tool 实现。

已确认交互是：点击 Ribbon Group 选择并显示 Tool Navigator；再次点击当前 Group 只折叠/展开 Tool Surface，而不关闭叶子、Editor 或后台任务。整行 Sub Tool Header 删除；真正关闭逻辑工具/MRU 回退由 Tool Surface 右上角不占独立行、可键盘到达的 `×` 承担。用户已在 2026-09-06 明确确认这次契约迁移，`AGENTS.md` 与权威前端规则必须和实现、测试在同一节点更新。

### 13.2 每阶段共同门禁

1. **模型门禁**：导航 Tree 只允许 `group` 或 `tool`；Group 不可执行，Tool 不可带 `children`，Action 不进入 Tree。
2. **路由门禁**：Group 入口只提交稳定 `groupId`，Tool 入口只提交稳定 `toolId`；只有显式 `defaultToolId` 可把选组继续解析成叶子激活。所有业务动作最终只提交 `(toolId, actionId)`，不得由按钮文字、首个子项或 DOM 位置推断处理器。
3. **状态门禁**：MRU、选中、Navigator 模式、Editor lifecycle、session/revision 分层保存；布局切换不得复制任务状态。
4. **安全门禁**：文件写入、改名、进程和删除仍由 Tool Controller 做领域校验；Primary 快照只允许短摘要，不携带源码、完整命令、凭据或绝对路径诊断。
5. **体验门禁**：主题 token、键盘、焦点、ARIA、窄宽与唯一滚动边界必须随阶段测试；Header 动作保持最小，不把 Tool Action 上移到原生 Header。
6. **兼容门禁**：新增 schemaVersion、枚举值或状态结构必须有旧版本迁移/拒绝策略；在旧实现移除前，以规范化清单和行为测试证明等价。
7. **归档门禁**：每阶段提交前复核分支、版本、起点、未归档文件、Wing 来源、隐私和文档清单；只提交本阶段范围，不自动合并或推送。

### 13.3 明确不在当前模型阶段处理

- 不重新设计已确认的原生 Header、目录 Row 或 Toolbar 展开/紧凑视觉。
- 不把 Ignore fix 分支、项目改名第二阶段正则/残留探测、编译脚本功能扩展混进导航模型提交。
- 不因 Tree 数据化而把脚本、handler 或任意可执行代码写入 JSON。
- 不恢复 Sub Tool Header，也不让每个工具自行复制标题/折叠行。0.1 已完成用户确认；后续 Group/Navigator 只能复用同一 Surface 显隐模型。
- 不实现大纲和网格两套状态机；二者必须由同一规范化模型与 ViewModel 派生。

设计依据：VS Code 建议限制 View 与 Header actions 数量、优先使用内置图标、避免重复功能，并要求 Webview 可主题化且具备 ARIA 与键盘导航；官方还明确不建议把 Tree item 当成单击即执行的按钮。所以下一原型应让 Navigator 负责选择 Tool、Action 由 Tool Surface/命令入口触发，并把布局切换保持为一个次要动作，不为大纲/网格复制两套运行时。原生 `view/title` 仅承载少量 `navigation` 动作，其余动作进入 `…`。参考 [VS Code Views UX Guidelines](https://code.visualstudio.com/api/ux-guidelines/views)、[Sidebars UX Guidelines](https://code.visualstudio.com/api/ux-guidelines/sidebars)、[Webviews UX Guidelines](https://code.visualstudio.com/api/ux-guidelines/webviews) 与 [Contribution Points](https://code.visualstudio.com/api/references/contribution-points#contributesmenus)。

## 14. MVC + Tool Registry 目标架构

### 14.1 参考模式与本仓取舍

VS Code 自身把可发现的 Command contribution 与运行时 `registerCommand` handler 分开，并保证同一 command ID 可被菜单、快捷键或代码调用；Tree View 则把数据提供者与 TreeItem 呈现分开；Webview View Provider 主要承担生命周期和消息桥接。0.9.0 不照搬原生 TreeView，也不引入重型框架，而复用这些成熟边界：**描述与执行分离、数据与呈现分离、Host 与 Webview 分离、可见性与可执行性分离**。

当前兼容实现可以工作，但职责仍集中：`tools/types.ts` 同时承载大量全局消息、UI 状态和 Tool 接口；`sidebarViewProvider.ts` 同时处理 Shell、领域分支和消息路由；`panelHtml.ts` 同时生成 Shell、各工具 DOM 与事件接线；`tools/registry.ts` 只是进程级可变数组。迁移目标不是一次拆完这些文件，而是先建立可测试的边界，再让旧路径逐个经过适配器退出。

### 14.2 分层职责

| 层 | 只负责 | 不负责 |
| --- | --- | --- |
| Navigation Manifest / Schema | Group/Tool 层级、文案、图标、顺序、默认叶子、允许的 Navigator 模式 | handler、脚本、VS Code API、运行状态、Primary/Editor presentation |
| Tool Registry | 在 Extension activation 的 composition root 一次性装配 Tool descriptor、Action Map、Controller factory、ViewModel projector、可选 companion；校验后冻结索引 | 导航状态、业务任务、DOM、全局可变单例 |
| Model | 纯 TypeScript 的导航图、Tool/session 状态机、Action token、领域 Analyze/Plan 数据 | `vscode`、DOM、文件写入、通知 |
| Tool Controller | 解析已验证的 Tool intent，拥有任务/session/revision，执行领域门禁并调用 Port | 拼 HTML、根据按钮文字分支、直接操纵另一个 Tool 状态 |
| ViewModel Projector | 从 Model snapshot 派生最小、可序列化、可脱敏的 Primary 或 Editor 投影 | 保存权威状态、执行命令、读取文件系统 |
| View / Web Component | 使用主题 token 渲染 ViewModel，维护短暂焦点/滚动状态，发出结构化 intent | 业务算法、路径推导、Action enablement 真源、跨工具路由 |
| Host Router | 校验 Shell/Tool envelope、查 Registry、验证 payload/session/revision/enabled/risk，再调用所属 Controller | 维护每个领域的特判 switch、猜测默认 Tool、信任 Webview payload |
| Ports / Adapters | 封装 VS Code 命令、配置、存储、文件系统、进程、SCM/Output 与平台差异 | 反向依赖 View 或把机器路径写入项目配置 |

静态代码依赖与运行时数据流必须分开描述，避免为方便发消息而让 View import Router 或 Controller。静态依赖固定为：

```text
View → serializable ViewModel/contracts
Host Provider → Host Router → immutable Registry interfaces
Tool Registration → Controller interfaces + ViewModel projector
Controller → pure Model + Port interfaces
VS Code/FS/Process adapters → Port interfaces
Composition root → Manifest parser + Registry builder + Host adapters
```

运行时数据流为：

```text
Manifest → normalized catalog → Navigator ViewModel → View
View semantic intent --postMessage--> Host Router → Registry Action → Controller
Controller → Model snapshot → ViewModel projector --postMessage--> View
```

这里的 `postMessage` 箭头是端口事件流，不是静态 import。下层不得反向 import 上层。纯 Model/Normalizer/Action routing 不导入 `vscode`；View 不导入 Tool Controller 或 Host Router 实现；Tool 之间协作只能经显式共享 Port 或领域服务，不能从全局 Registry 抓取彼此实例。

### 14.3 Registry 与 Action Router 草案

Registry 使用“实例化后冻结”的 composition-root 模式，不在模块 import 时向全局数组产生副作用。Extension 每次 activation 创建一个新实例并随 `ExtensionContext` dispose；测试可直接构造隔离 Registry，不再依赖清空进程级单例。构建索引时同时检查 `toolId`、Group ID、Module provider ID 和每个 Tool 内的 `actionId`；重复项在开发/测试直接失败，在正式 Host 禁用冲突贡献并输出双方 source owner，不允许后注册者静默覆盖前者。

```ts
interface KtcToolRegistration<TSnapshot> {
  readonly descriptor: KtcToolDescriptor;
  readonly actions: Readonly<Record<string, KtcToolActionDefinition>>;
  readonly createController: (ports: KtcToolPorts) => KtcToolController<TSnapshot>;
  readonly toPrimaryViewModel: (snapshot: TSnapshot) => KtcPrimaryToolViewModel;
  readonly editorCompanion?: KtcEditorCompanionRegistration<TSnapshot>;
}

interface KtcToolIntentEnvelope {
  readonly toolId: string;
  readonly actionId: string;
  readonly requestId: string;
  readonly sessionId?: string;
  readonly revision?: number;
  readonly payload?: unknown;
}
```

每个 Action Definition 同时提供 payload 的运行时 decoder/validator；TypeScript 类型不能替代 Webview 边界校验。Router 固定执行：解析 envelope → 查找 Tool/Action → 校验 placement、enabled、workspace trust、session/revision 与 payload → 记录脱敏审计 → 调用 Controller。Controller 返回状态转移或领域结果，Router 不解释结果正文，只触发对应 ViewModel 重新投影。

VS Code 原生命令只做薄适配：命令 ID 保持兼容，handler 把参数转换成同一个 Tool intent 后交给 Router。`package.json` 的 `when` 控制入口是否出现，`enablement`/运行态共同控制能否执行，但 Controller 仍必须做最终校验，因为隐藏或禁用 UI 不是安全边界。

4. 从 `sidebarViewProvider` 抽出 Host Router。Provider 只保留 Webview 生命周期、Shell context 与 postMessage；旧领域分支每迁一个 Tool 就删除一组。
5. 先让一个无写盘简单 Tool 完整使用 registration/controller/projector，再迁头文件 ASCII、编码和 UUID；每次只迁一个领域并保留旧命令 ID。
6. 保留现有 Module Shell v2 适配器：CAD provider 的 Host 生成 HTML 与无 `toolId` 的 `moduleBlockAction` 继续按 module owner 验证并路由，不冒充新 Tool Action。只有 CAD 发布新的 versioned Tool contribution 契约并通过兼容测试后，才删除 v2 adapter；不能直接以新 Registry 覆盖旧 CAD 接口，也不能在 0.9.0 单方改变 `ktAutoCodeModule` Manifest。
7. 最后迁 Project Rename/Auto Build hybrid Tool，把现有 companion state 作为通用 session/revision 模型的 fixture，而不是重写已经验证的安全门禁。
8. 等 Auto Code 与 CAD 至少各有一个消费者、API 命名稳定且无 Host 类型泄漏后，再把 Navigator/Tool Surface/Action Bar 的 Host-neutral 部分迁到 Wing；Wing 组件只接收 props 并发事件，不拥有业务 Controller。

### 14.5 测试金字塔与停止阀

- **纯模型层**：Schema、Normalizer、Registry、Action Router、session/revision、MRU 和 ViewModel 使用快速单元测试，覆盖非法输入与不变量。
- **Controller 层**：通过内存 Ports 验证文件/进程/配置调用顺序、取消、幂等、漂移与权限；不启动 VS Code，也不写真实用户目录。
- **View 契约层**：验证同一 ViewModel 在 outline/grid、深/浅/高对比、窄宽下的 DOM、ARIA、焦点与事件 envelope；不复制 Controller 测试。
- **Host 集成层**：只验证注册、命令兼容、View 生命周期、跨 Editor 激活、context key、存储 scope 与 Port 接线。
- **人工层**：每阶段只点检新增交互；Windows CAA/PowerShell、SCM Diff、真实主题与极窄宽度保留为平台矩阵。

目录显隐、Ribbon 布局、Module 状态、工作目录、Ignore 开关，以及 Project Rename/Auto Build 已存在的 session/配置 key 都是迁移兼容输入。新运行时只能兼容读取并通过显式 schema 升级写回；不得静默改名、清空或把机器级路径迁入 Workspace Folder 设置。

每阶段设置停止阀：兼容清单不相等、出现双状态真源、Router 需要新增 Tool 特判、View 必须读取文件系统、Controller 依赖 DOM、旧 session 可执行 Action、或无法独立回退时，立即停止扩迁并修复当前阶段；不能用“后续统一清理”带病进入下一批。
