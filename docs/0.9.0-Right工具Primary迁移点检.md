## 2. 内容放置决策表

对每个候选字段、状态或动作逐项判断，不按“原型里放在哪里”机械搬运。

| 位置 | 适合放置 | 不适合放置 |
| --- | --- | --- |
| Primary | 高频查看或操作；跨 Right 切换仍需可见的运行状态；当前选择、短统计、摘要；能显著减少往返 Right 的安全动作；简短的低频摘要 | 长表单、完整表格、长日志、复杂预览、批量编辑、危险确认、依赖 Right 未提交草稿的动作 |
| Right Header actions | 对整个 Right Surface 始终成立、短小、数量少、当前上下文中高频且无需先选择内部对象的动作 | 字段编辑、来源选择、只对某个区块或行生效的动作、危险动作、需要解释的大按钮组 |
| Right 内部 Block Header | 只作用于该 Block、在区块上下文中操作最高效的短动作，例如刷新、打开、添加或局部预览 | 跨区块动作、与当前区块状态无关的全局动作、完整操作流程 |
| Right 内部内容 | 依赖字段、行选择、局部状态或详细结果的动作；完整配置、表格、任务树、Diff、错误详情与确认流程 | 为了“和 Primary 一致”而复制的第二份状态机或业务逻辑 |

### 2.1 决策规则

- [ ] 先记录动作的作用域、频率、风险、所需上下文、是否依赖未提交草稿，再决定位置。
- [ ] Header 动作只在“全局、短小、高频、上下文稳定”同时成立时进入 Header；不能因为 Header 有插槽就填满。
- [ ] Primary 可以包含高频内容，也可以包含简短的低频摘要；低频不等于必须放 Right。Block 的初始展开状态由各工具已确认的原型决定，本轮 AutoBuild 内部可折叠 Block 均默认展开。
- [ ] 同一动作只在两侧都能明显提高效率时重复入口；两处入口必须发送同一语义 `actionId`，不得复制实现。
- [ ] 表面重复的入口应共享相同的 enablement、进度、错误、权限与确认语义。
- [ ] 任何依赖 Right 未提交 DOM 草稿的动作，在草稿进入 Controller 的校验状态之前，不得迁入 Primary 或 Right Header。
- [ ] 无法确认最佳位置时，保持正式现状，不移动、不删除、不改语义，并登记到“用户决策清单”。
- [ ] 迁移不顺带美化或重排 Right Main；Right 的独立细化必须另立需求和验收。

## 3. 双 Surface 统一契约

- [x] AutoBuild 一个逻辑 Tool 只创建一个业务 Controller 和一个稳定实例身份。
- [x] AutoBuild Primary 与 Right 消费同一 Controller 发布的可序列化 companion snapshot；Primary ViewModel 不导入 Preview fixture。
- [x] companion action token 校验 `panelId / sessionId / revision`，Right 草稿协议校验 `documentId / draftRevision / requestId`；过期、错误文档和同 revision 不同内容均被拒绝。
- [x] 两侧动作使用稳定的语义 `actionId` 和运行时校验后的配置 payload，不从按钮文案、DOM 位置或 CSS class 推断业务。
- [x] Primary 是 Host-neutral 组件，只发语义事件；它不读取 Right DOM、Shadow DOM、模块变量或组件实例。
- [x] Right 编辑草稿通过 `draftChanged / requestConfiguration / configurationSnapshot` 进入 Controller；Primary 的预检、启动、保存、并行切换与仓库清理都先原子读取当前草稿。
- [x] Right 关闭、隐藏或 dispose 后，Controller 继续保留实际子进程与任务状态；重开 Right 不建立第二份任务真源、不允许并发启动，且显式“停止”仍可达。完整 Extension Host 重启恢复仍留给第 9 节人工点检。
- [ ] 相同 snapshot 的重复投影不重建无关 DOM，不打断输入焦点、选择或滚动位置。
- [x] Primary 的统计与摘要由 Controller ViewModel 投影，不额外扫描文件、启动进程或自行计算第二份结果。

### 3.1 输出边界

- [x] Preview 底部公共 Output Block 只模拟 VS Code Output，不是插件能力，也不属于任何 Tool。
- [x] 正式插件继续使用现有唯一原生 `OutputChannel("KT Auto Code")` 及既有日志流程。
- [x] Primary 和 Right 的“Output / 输出”入口只负责显示原生 OutputChannel；正式 AutoBuild Webview 未创建日志框，也未复制或缓存日志正文。
- [x] Preview Output 的状态协议未进入正式 Controller；真实滚动和通道生命周期继续由 VS Code 原生 Output 管理。

### 4.1 先迁入 Primary 的只读投影

- [x] 运行概览：短状态、启用项目数、已完成 / 总任务数、失败数；无数据时显示明确空态，不显示伪造统计。
- [x] 当前配置摘要：配置文件名或“未保存配置”；完整路径只作 tooltip，窄栏正文不显示绝对路径。
- [x] 最新布局不在 Primary 显示项目摘要；正式 Primary 中上一安全切片的项目行已移除，完整项目表及其状态继续留在 Right。
- [x] 工程环境摘要：只展示 Controller 当前真实拥有的工作目录、执行模式和平台；尚未进入 Controller 状态的 CAA / 工具链信息不从 Preview fixture 补写。
- [x] 运行中、成功、失败、停止和不可用状态使用同一 Controller 状态映射，不由 Primary 自行猜测。

- [x] Primary 在 Right 隐藏、reload、原生 dispose / 重开时仍从 Controller 恢复完整草稿、任务、脚本与状态；执行轮次独立于 panel 生命周期，重开不会截断剩余阶段。

- [x] 只接入当前 Controller 已有、无需读取 Right 未提交草稿的安全动作。
- [x] “详细配置 / 回到 View”只负责显示或定位既有 Right，不创建新业务实例。
- [x] “停止”只在 Controller 判定存在可停止任务时启用，并复用现有停止路径。
- [x] “Output”只显示原生 OutputChannel。
- [x] “打开”复用 Controller 已有的 JSON 文件选择 / 加载路径，不读取 Right 草稿。

### 4.2.1 已实现的第二切片（待真实 Host 人工确认）

- [x] Primary 内容首先显示完整“当前配置”区，包含当前名称或“未保存”、打开 / 保存 / 详细配置和最近配置；之后才显示“执行”区。
- [x] “执行”动作顺序固定为 `脚本 → 预检配置 → 启动 → 停止`；状态、Output、并行选项和运行统计仍在同一区域。“脚本”复用既有脚本管理逻辑，Right Header 已删除该重复入口。
- [x] “预检配置 / 启动”先向当前 Right 原子请求最新草稿，校验 action token、request、session、document、draft 与 revision 后，再进入 Controller 的同一 dispatcher；超时、stop、reload / dispose 和过期回复均不会回退执行缓存配置。
- [x] “停止”复用 Controller 当前停止路径，并取消尚未完成的 Primary 草稿请求；迟到快照被忽略。
- [x] “并行编译”写入同一 AutoBuild 草稿，Primary 与实际任务规划读取同一个字段，运行中按 Controller enablement 禁用；Right 的重复可见 checkbox 已移除。
- [x] 首次打开只创建当前目录的 fresh draft；旧 `PATH_KEY / STATE_KEY` 不会自动载入，最近配置只作为用户显式选择项。手动打开 JSON 时保留文件自己的 `workingDirectory`，不会被当前 View 目录覆盖。
- [x] Primary“关闭”会原子读取最新草稿：有修改时提供“保存 / 不保存 / 取消”，保存或另存取消时保持当前配置；未修改的 fresh draft 可直接关闭并回到新的未保存配置。
- [x] “另存”默认位置依次采用本机可访问的当前草稿工作目录、当前 JSON 所在目录、插件传入工作目录、VS Code 第一个 Workspace Folder；均不可用时交给系统默认位置。已有 JSON 复用其文件名，否则使用 `auto-build.json`。
- [x] 已载入配置或已有项目时修改 `workingDirectory` 会进入 mismatch 门禁：预检、启动、项目选择 / 探测 / 运行、脚本导出等路径敏感动作被阻止，用户必须在 Primary 显式选择“新建配置”或“保留项目”。前者清空旧项目、探测和任务；后者保留项目定义但清空探测、仓库快照和任务。无项目 fresh draft 可自然切换目录。
- [x] Primary 维护区新增独立“清理仓库”按钮；Controller 在 Windows 上以 `-Clean -ForceClean -CleanOnly` 只清理 Root / 3rdParty / 所选 CMake 目标，先显示范围与目标数量并二次确认，结果进入原生 Output，绝不继续 fetch / checkout / build。旧 schema v2 `clean: true` 会显式关闭并提示改用手动清理，测试固定该兼容行为。
- [x] 仓库清理计划在确认前把 Root、3rdParty 和所选 CMake 候选解析到实际 Git top-level，并逐项列出 CMake `build` 的“删除整个目录 / 清空并保留目录”动作；执行脚本再次以实际仓库顶层执行安全检查，配置子目录不能让确认范围小于真正的 `git clean` 目标。
- [x] 两类清理在计划生成、确认框等待和执行前都服从当前 Controller / session 身份与显式“停止”；停止后即使确认结果迟到也不执行删除。手动 Root 清理还冻结每个顶层候选和完整目录树身份，先验证全部快照；身份、类型、树内容或目标范围变化时拒绝继续。

### 5.3 多目录 / 多 Git root 边界

当前已知实现边界：Ignore 解析以单个扫描 root 为输入；Git 来源查找该 root 最近的 Git 仓库根并重定位其根 `.gitignore`，且有意不递归聚合多个嵌套仓库。因此，“一次传入一个 root”不能自动代表多目录、多 workspace folder 或多个独立 Git root。

已确认的真实差异：

- 搜索替换在“第一个 Workspace Folder 的子目录”场景中，Primary 的 Ignore 摘要按用户选择的子目录读取，但执行仍以第一个 Workspace Folder 为 `location.root`、把子目录仅作为 `scope`；因此可能显示 `child/.phoenix/.ignore`，实际却使用父级 `.phoenix/.ignore`。
- 项目改名在进入 Right 前会把 `location.root + scope` 解为实际项目根，当前方向正确。
- 头文件引用修正分别为 Package 根和目标根解析策略，当前方向正确，但仍需双根集成测试固定。
- 三来源选择目前保存在一套未按 canonical scan root 分组的 `workspaceState`；多 Workspace Folder 的规则文件可分别解析，不代表来源选择已按 Folder 隔离。
- `pluginIgnoreEnabled` 是 `customIgnoreEnabled` 的兼容别名，不是用户要求的 Ignore 总开关；禁止改名后直接复用。
