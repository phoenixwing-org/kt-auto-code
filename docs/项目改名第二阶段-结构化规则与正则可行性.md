# 项目改名第二阶段：结构化规则与正则可行性

状态：draft

Owner：KT Auto Code maintainers

适用版本：0.8.x 之后；不进入当前 0.8.1 候选

最后核验：2026-09-01

> 本文定义第二阶段候选需求和安全行为，不授权当前实现增加正则输入框或动态写盘。第一阶段仍以显式 `Source → Target` 精确规则为唯一写盘真源。

第一阶段整改已要求为精确文本规则提供写盘前原生 Diff Editor：左侧冻结原文、右侧计划文本，且不先修改磁盘。第二阶段结构化规则必须复用并增强该预览通道，不得把写盘前 diff 再推迟为后续能力。

## 1. 结论

用户提出的通用改名可以实现，但应解释为**结构化名称模式**，而不是直接把任意 JavaScript 正则和替换字符串交给大型仓库写盘：

```text
A <连接符1> B <连接符2> C
→ A1 <连接符1> B1 <连接符2> C1
→ A1 <连接符1> C1
```

可行性分级：

| 能力 | 可行性 | 第二阶段决策 |
| --- | --- | --- |
| 结构化词段发现与只读预览 | 高 | 建议实施 |
| 保留实际连接符和命中大小写 | 高 | 建议实施，但混合大小写默认阻止自动转换 |
| 文本内容受控写盘 | 中高 | 逐命中冻结计划完成后可实施 |
| 文件名、目录名动态改名 | 中 | 推迟到文本稳定之后 |
| 专家正则只读扫描 | 高 | 可选；必须使用 RE2 类确定性语义和资源上限 |
| 任意 JavaScript `RegExp` + `$1` 直接写盘 | 低 | 不进入路线 |
| 替换函数、脚本或再次递归匹配 | 低 | 禁止 |

## 2. 用户任务

第二阶段解决的是“同一组词在不同大小写和连接符中出现，并允许替换、保留或删除部分词段”，典型例子：

```text
Phoenix Open Issue   → Phoenix Issue
phoenix-open-issue   → phoenix-issue
phoenix_open_issue   → phoenix_issue
PHOENIX.OPEN.ISSUE   → PHOENIX.ISSUE
phoenixOpenIssue     → phoenixIssue
```

也支持逐词改名而不是删除：

```text
Phoenix Open Issue   → Nova Public Ticket
phoenix-open-issue   → nova-public-ticket
PHOENIX_OPEN_ISSUE   → NOVA_PUBLIC_TICKET
```

稳定 URL、协议、环境变量、包名或领域前缀不因共享词段自动跟随。`open-issue` 是否改成 `issue` 必须作为独立候选显示，默认关闭。

## 3. 推荐规则模型

### 3.1 结构化源模式

规则由有序词段和受控连接关系组成，而不是自由正则：

```json
{
  "id": "project-name-with-middle-word",
  "sourceTokens": [
    { "id": "a", "text": "Phoenix" },
    { "id": "b", "text": "Open" },
    { "id": "c", "text": "Issue" }
  ],
  "connections": ["preserve", "preserve"]
}
```

`preserve` 连接只接受以下实际形态：

- 单个或连续空白；
- `-`、`_`、`.`；
- 无字符，但存在 camelCase/PascalCase/全大写词段边界。

连接关系不得退化为“任意字符”，不能跨 `/`、`\`、换行或标识符外的大段文本。

### 3.2 目标模板

目标模板只允许三种操作：

1. 引用一个源词段，并替换为声明的目标词。
2. 原样复用某个实际连接符。
3. 显式省略一个词段及相邻连接关系。

示意：

```json
{
  "target": [
    { "from": "a", "text": "Phoenix", "case": "match-source" },
    { "separatorFrom": 1 },
    { "from": "c", "text": "Issue", "case": "match-source" }
  ]
}
```

不允许执行 JavaScript、调用函数、访问文件系统、读取其他命中或把第一次替换结果再次送入同一轮匹配。

## 4. 大小写行为

每个命中的词段独立分类：

| 源形态 | `match-source` 目标行为 | 示例 |
| --- | --- | --- |
| lower | 目标词全小写 | `issue → ticket` |
| UPPER | 目标词全大写 | `ISSUE → TICKET` |
| Capitalized | 首字母大写，其余小写 | `Issue → Ticket` |
| camel 首词 | 目标词首字母小写 | `phoenixOpen → novaPublic` |
| Pascal 词段 | 目标词首字母大写 | `PhoenixOpen → NovaPublic` |
| 数字 | 原样或显式目标值 | `V2 → V3` |
| 不规则混合 | 不自动转换 | `pHoEnIx` 只报告风险 |

用户也可显式选择 `lower / upper / capitalized / camel / pascal / literal`，但默认是 `match-source`。大小写分类失败时，该命中进入只读风险列表且默认不进写盘计划。

## 5. 正则能力边界

### 5.1 可开放的专家只读正则

若提供“专家正则”，第一步只用于发现、计数和生成候选，不直接写盘。建议采用 RE2 类无灾难性回溯语义，并限定：

- 模式最长 512 字符；
- 最多 16 个命名捕获；
- 单文件、全任务均有时间和命中数量上限；
- 支持字面量、转义、字符类、Unicode 类、分组、命名捕获、选择和常用量词；
- 允许大小写敏感或 Unicode 简单大小写不敏感扫描；
- 禁止零宽全局替换结果进入写盘计划。

### 5.2 明确不支持

- lookbehind、lookahead 和其他 lookaround；
- 模式内反向引用；
- 递归、条件分支、原子组和引擎专有扩展；
- 任意 JavaScript `RegExp` 回溯语义；
- `$&`、前缀/后缀全文、替换函数或脚本求值；
- 跨文件捕获、跨行无限扫描和跨路径分隔符匹配；
- 以零宽命中插入任意文本；
- 一轮替换后再次递归匹配新文本。

### 5.3 替换模板

只读正则可展示以下受控模板的预览：

```text
${a}
${separator1}
${c|match-source:Issue}
${c|upper:ISSUE}
```

模板只引用命名捕获或声明的连接符，并应用枚举化大小写转换。未定义捕获、空目标、产生路径分隔符或超长目标均为错误。该模板即使能预览，也不能绕过逐命中冻结计划直接写盘。

## 6. 匹配优先级

为了与当前精确规则“最长优先、同长度按界面顺序”一致，结构化扫描固定为：

1. 从文件起点向后寻找最左命中。
2. 同一起点选择覆盖字符最多的命中。
3. 长度相同时按用户可见规则顺序。
4. 一个字符区间只能属于一条写盘规则；重叠候选全部报告，但只有胜出项进入计划。
5. 替换完成的目标文本不再参与本轮匹配。

文件名和目录名阶段仍只在 basename 内匹配，不把完整路径当作一个正则字符串。

## 7. 逐命中冻结计划

当前精确引擎主要按报告项、次数和目标路径检测漂移；动态目标可能在次数相同的情况下发生变化，因此第二阶段必须冻结每个实际命中：

```text
ruleId
fileRelativePath
fileContentHash
encoding
byteStart / byteEnd
originalBytes / originalText
capturedTokens / capturedSeparators
targetBytes / targetText
pathTarget（如适用）
```

执行前重新读取全部相关文件，并逐项检查：

- 文件 hash 与分析时一致；
- 字节区间仍为原始内容；
- 编码和 BOM 未变化；
- 规则、捕获、目标文本与冻结计划一致；
- 路径源和目标仍存在且无冲突。

任意一项漂移则整批阻止，不在写盘阶段重新运行模式，也不做“能写多少写多少”。

## 8. 写盘顺序与编码

第二阶段首个写盘切口只处理文本：

- 每个文件按 `byteStart` 从后向前替换，避免前一处改变后一处偏移。
- UTF-8、UTF-8 BOM、GBK 分别验证字符到字节映射；不支持编码只报告。
- 保留原 BOM、换行和未命中字节。
- 继续跳过二进制、大文件、symlink 和 Ignore 路径。
- 写盘前先生成逐命中冻结计划，并通过既有虚拟文档通道提供原生 Diff Editor 预览；执行仍要求 Git clean，完成后自动复扫并保留原生 Git 对比。

文件名/目录名放在后续子阶段：

- 目标必须是非空 basename；禁止 `/`、`\`、`.`、`..`。
- 全局预检多源同目标、目标已存在、大小写-only 和父子路径重叠。
- 文件先于目录；目录从最深到最浅。
- 大小写不敏感文件系统继续使用受控临时名。

## 9. UI 草案

结构化规则放在“项目改名 → 改名方案”内，作为一种新的显式规则类型：

```text
[启用] [结构化]  Phoenix | Open | Issue  →  Phoenix | Issue  [预览]
```

- 默认先显示人类可读词段，不把正则源码作为主界面。
- 展开详情后才能查看编译后的只读模式、捕获和上限。
- 每条规则提供“只读扫描”，首次扫描绝不写盘。
- 预览逐项显示实际 Source、Target、捕获连接符、大小写决策和风险原因。
- 稳定 URL、协议、包契约和混合大小写命中默认关闭。
- 专家正则若开放，放在独立高级区并明确标记“只读候选”，不与精确规则的写盘开关混淆。

## 10. 分阶段路线

### S1：结构化只读预览

- 实现受控词段 parser 和连接符捕获。
- 生成逐命中预览，不改变现有 `WorkspaceRename` 写盘入口。
- 验证大小写矩阵、重叠、边界、资源上限和稳定契约候选。

### S2：文本受控写盘

- 引入逐命中冻结数据、文件 hash 和字节范围。
- 执行前全量复验；任何漂移整批阻止。
- 复用第一阶段写盘前 Diff Provider，以及现有 Git clean、确认、编码、Ignore、取消、完成复扫和写盘后 Git 对比门禁。

### S3：文件名和目录名

- 仅在 S2 稳定且 Windows/macOS/Linux 文件系统矩阵通过后开放。
- 增加全局路径图、大小写临时名、最深目录优先和根目录门禁。

### S4：专家正则评估

- 先只读；使用 RE2 类引擎。
- 根据真实使用记录决定是否需要受控模板写盘。
- 未单独评审前，不允许把 JavaScript 正则直接接到现有 Apply。

## 11. 验收样例

至少包含以下 fixture：

- 空格、`-`、`_`、`.`、camel、Pascal、UPPER_SNAKE；
- 删除中间词、逐词改名、词段数量不一致；
- 混合大小写、Unicode 词段、数字和缩写；
- `open-issue` 独立短契约与完整 `phoenix-open-issue` 的覆盖排除；
- 同一起点长短规则、不同规则重叠、同 Source 不同 Target；
- UTF-8、BOM、GBK、CRLF/LF、多字节偏移；
- 20,000 项截断、超时、取消、二进制、大文件、symlink、Ignore；
- 分析后文件漂移、编码漂移、目标路径冲突和 Git dirty；
- Windows 大小写不敏感改名和长路径。

写盘验收必须证明：计划中的每个目标文本在执行前已确定并可由原生 Diff Editor 查看；执行阶段没有再次运行正则；失败时没有部分写盘；执行后原生 Git diff 与写盘前冻结预览一致。

## 12. Go / No-Go 门禁

只有以下条件全部满足，S2 文本写盘才可从 draft 晋升：

- [ ] S1 在真实大型 Web/CAA 仓库只读运行，没有失控耗时或内存增长。
- [ ] 逐命中冻结模型完成架构审查，不与当前报告身份混用。
- [ ] UTF-8/BOM/GBK 字节偏移测试完整。
- [ ] 重叠和大小写规则有唯一、可解释结果。
- [ ] 智能候选默认关闭，稳定契约不会被自动修改。
- [ ] 漂移、冲突和 Git dirty 全部在首个写盘前整批阻止。
- [ ] 写盘前 Diff 使用冻结原文和确定目标；结构化规则不能在打开 Diff 时重新计算另一份结果。
- [ ] Windows 用户完成真实文件系统测试。

任一条件未满足时，第二阶段只保持只读预览，不开放 Apply。
