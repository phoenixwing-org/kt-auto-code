# 编码修正

> 工具 ID（规划）：`encodingFix`  
> 显示名：**编码修正**  
> 与 **头文件 ASCII 修正**（`headerAscii`）分工不同：本工具管**文件整体编码**（ASCII / GBK / UTF-8），不替代头文件内的弯引号、NBSP 等字节级清理。

---

## 1. 背景

工程里常见三类「编码」表述（实质是**磁盘字节 + 解码方式**）：

| 名称 | 说明 | 典型 BOM / 特征 |
| --- | --- | --- |
| **ASCII** | 仅 `0x00–0x7F` | 无 BOM |
| **GBK（本机 local）** | 中文 Windows 代码页 **CP936** | 无 BOM；双字节中文 |
| **UTF-8** | Unicode 的 UTF-8 序列 | 见下节 |

MSVC 在未加 `/utf-8` 时，源文件常按 **系统代码页（local）** 解释；Git、现代编辑器、Markdown 生态则默认 **UTF-8 无 BOM**。

**头文件 ASCII 修正**只处理「在某种解释下不该出现的字节」（弯引号、NBSP、非 ASCII 等），**不会**识别「整文件是 UTF-16」这类情况——误把 UTF-16 当字节流修，会破坏文件（例如 `FF FE` 被改成空格 + `/**`）。**编码修正**负责先判断整文件编码，再决定是否转换或仅报告。

---

## 2. UTF-8 的几种形态（须区分）

| 形态 | 文件头字节 | 说明 |
| --- | --- | --- |
| **UTF-8 无 BOM**（默认配置） | 无 | Git、VS Code、`.md` 推荐；跨平台默认 |
| **UTF-8 带 BOM** | `EF BB BF` | 部分 Windows 记事本另存为；可转为无 BOM |
| **UTF-16 LE** | `FF FE` | **不是 UTF-8**；VS/旧工具偶见；须单独识别 |
| **UTF-16 BE** | `FE FF` | 同上 |
| **UTF-32 LE/BE** | `FF FE 00 00` / `00 00 FE FF` | 少见，仅识别并报告 |

规划中的检测顺序建议：

1. BOM 判断（UTF-8 / UTF-16 / UTF-32）
2. 无 BOM 时：尝试严格 UTF-8 解码；失败则倾向 **GBK（local）** 或 **纯 ASCII**
3. 对 **UTF-16** 等宽字节文件：**不**走 `headerAscii` 的字节替换管线，仅在本工具中报告或做整文件转码

---

## 3. 项目级目标策略

| 项 | 约定 |
| --- | --- |
| **默认目标** | `ktAutoCode.encodingFix.defaultTarget`，可选 UTF-8 无 BOM、GBK（local）；缺省为 UTF-8 |
| **分类覆盖** | 头文件、源文件、Markdown 可分别选择继承、ASCII、UTF-8、GBK |
| **UTF-8 ↔ GBK** | 仅在目标编码可无损表示全部字符时转换；无法表示时只报告 |
| **ASCII 目标** | 纯 ASCII 文件或仅需去 BOM 时可转换；含中文等非 ASCII 内容时只报告，不静默删除 |
| **Markdown（`.md`）** | 默认继承；一般项目建议显式覆盖为 UTF-8 |
| **C++ 头文件（`.h` 等）** | ASCII 目标是编码约束；需要删除或替换非 ASCII 内容时仍使用 **头文件 ASCII 修正** |

配置保存在当前项目的 VS Code 工作区设置（通常为 `.vscode/settings.json`）：

```jsonc
{
  "ktAutoCode.encodingFix.defaultTarget": "utf8",
  "ktAutoCode.encodingFix.headerTarget": "ascii",
  "ktAutoCode.encodingFix.sourceTarget": "utf8",
  "ktAutoCode.encodingFix.markdownTarget": "inherit"
}
```

## 4. 功能范围（规划）

### 4.1 预检（必做）

扫描工作区内配置扩展名的文件，输出：

| 列 | 含义 |
| --- | --- |
| 文件路径 | 相对工作区 |
| 检测编码 | `ascii` / `gbk` / `utf8` / `utf8-bom` / `utf16-le` / `utf16-be` / `unknown` |
| 期望编码 | 按规则表（见 §5） |
| 状态 | `ok` / `mismatch` / `unsupported` |
| 建议操作 | 如「GBK → UTF-8」「去掉 BOM」「UTF-16 → UTF-8」「仅报告」 |

可选复选框：**显示详细**（BOM 十六进制、置信度说明）。

### 4.2 修正（可选、需确认）

头文件 ASCII 修正（`headerAscii`）已具备 **BOM 预检** 与可选 **去除 BOM**（设置 `ktAutoCode.headerAscii.stripBom`）：

| BOM 类型 | 未勾选去除 | 勾选去除 |
| --- | --- | --- |
| UTF-8 BOM | 仅列出；内容区仍可字节清理 | 去掉 `EF BB BF` |
| UTF-16 LE/BE | **不做字节级修复**（避免误改 `FF FE`） | 解码为 **UTF-8 无 BOM** |

完整工程级编码转换见下文 Phase B/C。

| 操作 | 默认是否提供按钮 | 说明 |
| --- | --- | --- |
| **GBK → UTF-8 无 BOM** | ✅ | UTF-8 目标下无损转码 |
| **UTF-8 → GBK** | ✅ | GBK 目标下无损转码；存在 GBK 无法表示的字符时只报告 |
| **UTF-8 BOM / UTF-16 → 当前目标** | ✅ / ⚠️ | 去 BOM；UTF-16 整文件重编码仍强提示 |
| **可无损内容 → ASCII** | ✅ | 例如纯 ASCII 的 BOM / UTF-16 文件 |
| **含非 ASCII 内容 → ASCII** | ❌ 自动转换 | 只报告，并引导到 `headerAscii` 做内容级决策 |

写盘前：Modal 确认 + Git 友好（用户自行 diff）。

### 4.3 与 `headerAscii` 的关系

```text
编码修正（encodingFix）     整文件：是什么编码？是否符合当前项目目标？
        ↓ 头文件仍为 GBK 且含中文时
头文件 ASCII 修正（headerAscii）  内容级：弯引号、NBSP、非 ASCII 字节
```

**顺序建议**：先 **编码修正** 把头文件/源文件统一到 UTF-8（若团队如此规定），再对头文件跑 **ASCII 修正**；或头文件保持 GBK 仅做 ASCII 清理——由团队策略配置。

## 5. 按扩展名的期望编码（初版）

| 扩展名 | 期望编码 | 预检不符时 |
| --- | --- | --- |
| `.md`、`.mdx` | UTF-8（无 BOM 优先） | **列出**；可一键改为 UTF-8 无 BOM |
| `.json`、`.yaml`、`.yml` | UTF-8 无 BOM | 列出 |
| `.cpp`、`.c`、`.cc`、`.cxx` | 团队配置，默认 **UTF-8 无 BOM** | 列出；可提供 GBK→UTF-8 |
| `.h`、`.hpp` 等头文件 | 团队配置（CAA 常仍为 GBK 或 ASCII） | 列出；**不默认** UTF-8→GBK |
| `.txt`、`.cmake` | UTF-8 无 BOM | 列出 |

规则由 `ktAutoCode.encodingFix.defaultTarget` 及 `headerTarget`、`sourceTarget`、`markdownTarget` 配置。

## 7. 实现要点（开发备忘）

1. **检测**：BOM + `iconv-lite` 或 Node `TextDecoder`；无 BOM 用 UTF-8 strict，失败再试 GBK decode。
2. **转换**：`Buffer` 读入 → 按源编码 decode → 按项目目标无损 encode；UTF-8 不写 BOM。
3. **勿**对 UTF-16 文件逐字节 `sanitizeSourceForGbk`（已发生：`FF FE` → 空格 + 破坏结构）。
4. **`.md` 专检**：扩展名规则 + 编码列在预检表置顶或筛选。
5. **测试样例**：`tests/fixtures/encoding/` — `utf8-bom.md`、`gbk.cpp`、`utf16-le.h`（从 XyGuid  anonymized 片段）。
