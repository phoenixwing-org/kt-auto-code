# KT Auto Code agent instructions

## Local Phoenix Wing development

- The supported local integration layout is sibling repositories: `kt-auto-code`, `kt-auto-cad`, `phoenix-wing`, and optionally `phoenix-desk-tools`.
- Use `pnpm dev` or `pnpm ext:dev` for full local Wing development. These commands must resolve `../phoenix-wing` and `../kt-auto-cad`, build required Code/CAD Wing packages, build each extension in its owning repository, and launch both extension development paths.
- Use `pnpm ext:dev:code` when intentionally developing only KT Auto Code, or `pnpm ext:dev:code:prepare` for its build-only gate. The formal Auto build, Registry comparison and release must never require the CAD repository.
- For build-only AI verification, use `pnpm ext:dev:prepare`. Use `pnpm ext:dev:check` only for a fast repository contract check.
- If sibling Wing is absent, local development must fail. Never add a silent Registry fallback.
- When a consumer checkout lives at `Phoenix/worktrees/<repo>`, preserve the same sibling contract by creating `Phoenix/worktrees/phoenix-wing` as a filesystem symlink to the explicitly selected active Wing checkout before running local integration. Full Code + CAD development likewise uses `Phoenix/worktrees/kt-auto-cad` when the active CAD checkout is outside `worktrees/`. Resolve and report the link target, branch, and package version first; never guess among multiple checkouts, replace an existing non-link path, commit the link, or encode its target in a manifest or lockfile.
- Use `pnpm dev:registry` when comparing against the exact npm Registry versions in the committed lockfile.
- Never write `link:`, `file:`, a workspace override, or a local Wing path into a committed manifest or `pnpm-lock.yaml`.
- `PHOENIX_WING_ROOT` is accepted only through the controlled local wrapper, paired with `PHOENIX_WING_DEV_MODE=1`. Formal builds must reject a leaked root variable; the Registry wrapper clears both variables.
- A local build is accepted only after the esbuild metafile gate proves all expected Wing inputs came from the sibling repository and none came from the consumer's `node_modules`.
- Do not describe a local integration check as passed until `pnpm ext:dev:prepare` has completed successfully.

See [docs/本地Wing并列开发.md](docs/本地Wing并列开发.md) for commands and the manual checklist.

## Target release line and worktrees

- Trial rule: read the version branch currently checked out in the repository's main working directory as the target release line for that round. `develop` is only the development/test baseline hint; it is not an implicit commit, merge, or release target.
- Before every commit, merge, package, or release action, re-check the actual branch, package version, working tree, and the user's current release intent. Do not infer the target from an earlier task or another machine's in-progress branch.
- Put ongoing development worktrees in the shared Phoenix root's `worktrees/` directory, alongside the product repositories. Do not create new hidden `.worktrees` directories. Existing historical worktrees may be inspected or retired separately, but must not be used as the new default.

## Locked four-region shell

- The Primary sidebar contributes one native Webview View named `KT Auto Code`. Its native View Header owns the fixed global actions in this order: Directory visibility, Ignore, then Settings. Directory visibility only shows or hides the Directory region and preserves its selection; Ignore opens the standalone `ignoreSettings` logical tool View; Settings opens `environmentSettings`. Search preview, the directory gear, and a Webview-internal Ignore shortcut do not belong in the native Header or directory row.
- Inside that Webview there are exactly four ordered, full-width regions: Directory, the integrated Toolbar strip, Current Tool, and Open Items. Ignore and Settings reuse Current Tool and never create another first-level region. Open Items remains fixed at the bottom and does not scroll with Current Tool content.
- The Toolbar strip has no separate visible title row and no density button. Its 16px chevron stays at the upper left, the one Ribbon DOM occupies the middle, and the only ribbon customization `…` stays fixed at the upper right. Expanded mode preserves the current icon-plus-short-label Ribbon and may wrap to multiple rows; compact mode keeps one icon-only row and leaves every hidden-overflow tool reachable from `…`. The chevron switches these two modes through `ktAutoCode.sidebar.toolPickerStyle`; it never removes the primary navigation entirely.
- Current Tool is always expanded. Its Header contains the Tool icon and title on the left and an independent `×` on the right; it has no disclosure control or collapsed state. `×` only closes the current logical tool with the existing MRU fallback. Only Current Tool Body owns the main vertical content scrollbar; the Webview page, Directory, Toolbar, Current Tool Header, and Open Items must not become normal vertical scrolling boundaries.
- Directory intentionally has no disclosure arrow or body. It owns only directory context, selection, and folder picking: it has no decorative folder on the left, aligns its `目录` label with spacing, and keeps the actionable folder picker as the only folder icon on the right.
- Treat that region count, order, responsibility split, directory visibility behavior, single Ribbon ellipsis, fixed Open Items placement, scrolling boundary, and close semantics as a locked outer-shell contract. Ordinary feature, styling, or cleanup work must not change them incidentally.
- Titles, icons, spacing, responsive styling, accessibility, and all content inside an individual Block may be improved as long as the locked outer-shell contract remains intact.
- Approved on 2026-09-09: closing the last Right View for `projectRename`, `autoBuild`, or `packageIncludes` also closes its logical Primary Tool and Open Item, restoring the existing MRU or Welcome without running another tool or stealing focus. Keep Primary if another live Right session for the same tool remains. Codegen is explicitly excluded: its Editors belong to individual JSON documents. Closing Primary itself still does not close Right or cancel a task.
- Before implementing a request that would change the locked contract, explicitly tell the user which rule would be broken, why the change is necessary, and what migration or regression risk it creates. Wait for explicit user confirmation before changing code or this rule.

See [docs/前端开发规则.md](docs/前端开发规则.md) for the authoritative UI contract and acceptance checklist.

## Compact manager lists

- Primary/sidebar manager file rows default to one continuous `file name · relative path` label. Let that single label consume the remaining width and ellipsize as a whole; do not reserve separate fixed or percentage widths for the name and path. Inline child spans may distinguish the file name (primary/semibold) from the path (secondary/smaller), but both must remain inside the same flexible truncation container.
- Keep status/count/encoding badges in one fixed right-side tail. Preserve the full path in `title` and `aria-label`.
- For VS Code-style manager blocks, prefer full-width section borders and very small internal padding over card-like outer horizontal gaps. Retain a small inner inset for text and icon toolbars so interactive content does not touch the edge.

## Locked Primary shell

- Preserve the approved four first-level regions in this exact order: Directory, integrated Toolbar strip, Current Tool, Open Items. Toolbar switches only between expanded and compact navigation; Current Tool remains expanded; Directory is the approved one-line context row controlled by the native Header; Open Items remains fixed at the bottom. Only Current Tool has the separate logical-tool close action.
- Preserve the full-width adjoining separators, native 16px chevron alignment, compact controls, no card gap and no draggable separator. Directory and Current Tool retain the VS Code section-header baseline; Toolbar intentionally uses the approved integrated strip with no separate title row.
- The native View Header keeps Directory visibility, Ignore, and Settings in that order. The integrated Toolbar keeps its chevron, one shared Ribbon and one overflow action; it has no density action or visible `工具栏` title. Directory keeps the selector and its sole right-side folder picker with no left decorative folder and no gear. Current Tool keeps its Tool icon, title and independent `×`, with no collapse action. Header actions may evolve only through an intentional contract, documentation, and regression-test change; ordinary feature work must not add shortcuts there. Internal features may evolve, but changing this outer structure or visual baseline requires warning the user and receiving explicit confirmation first.
- Implement the formal shell with shared Host-neutral Web Components. `KtcPrimaryShell` only fixes the four named-slot order and the Current Tool flex/scroll track; Directory, Toolbar, Tool Navigator, Current Tool, Open Items and Right Shell remain separate components with serializable models/slots and stable semantic events. Components must not own VS Code API calls, business controllers, MRU, routing, persistence or cross-surface lifecycle. `KtcSystemOutputBlock` is a Preview-only imitation of VS Code Output and must not be wired into, bundled for, or advertised as a formal plugin capability; formal logging continues through the existing native `OutputChannel("KT Auto Code")`.
- A Group is navigation only: it toggles its child Navigator and never owns Current Tool, Right View, Open Items, lifecycle, or a business action. If the Group already has open leaf Tools, selecting it may activate that Group's MRU leaf; otherwise it preserves the current Tool or Welcome and never opens the first child implicitly. Tool display copy (`title`, `shortTitle`, `description`) is resolved by `toolId` from the versioned registration JSON. Primary, Right, Open Items, Navigator, and Ribbon consumers must not override it or prefix it with a Group, module, or plugin name; extra ownership context belongs only in tooltips and accessible labels.
- Keep Phoenix Webview Preview as the long-lived design sandbox and behavioral gold sample. Future shell or large UI changes are first implemented and confirmed in Preview, then deliberately synchronized to the formal Host, governance text and regression tests; Preview confirmation alone never means formal Host migration has passed.
- Trial the risk-based Preview workflow instead of mechanically implementing every pixel twice. New shell structure, large regions, uncertain interactions, and disputed visual directions still go through Preview first. Small adjustments inside an already approved shared component may change that Host-neutral component directly so Preview and Host receive the same implementation. When a small visual choice is still uncertain, expose it as a Preview-only token with the formal fallback unchanged, then promote the confirmed token value to the formal default or adapter. Never fork the component DOM, business logic, or event protocol merely to run a visual experiment; revisit this trial rule if it starts creating duplicate maintenance or token drift.
- When a formal UI migration reaches a meaningful, buildable milestone and its automated gates pass, launch a visible VS Code Extension Host for the user to inspect the real result. Treat that handoff as a stage preview, not as automatic visual acceptance; record any observed VS Code-only loss before continuing.
- Follow [docs/ShellBlock控件提炼TODO.md](docs/ShellBlock控件提炼TODO.md) for the formal component integration checklist; do not combine the extraction with unrelated feature changes.

## Plugin configuration storage

- Classify every new `ktAutoCode.*` setting before choosing storage. Team-visible project policy belongs in the current Workspace Folder's `.vscode/settings.json` through a resource-scoped configuration and `vscode.ConfigurationTarget.WorkspaceFolder`; examples include encoding targets and related CAA/MK projects.
- A locally installed tool version is not automatically a project property. `ktAutoCode.run.caaVersion` is a machine-scoped default; each project's current Run selection may live in `workspaceState` because the same source can be built against multiple versions. A future team-pinned version matrix must be an explicit target/profile schema rather than a single mutable default.
- Machine integration stays in VS Code User Settings and must use the unified `ktAutoCode.deskTools.*` machine-scoped keys. Never write Desk Tools executable paths, installation manifests, service ports, or other user-machine absolute paths into a project `.vscode/settings.json`.
- Use `workspaceState` only for transient per-workspace UI/session state such as expansion, filters, cursors, and recent UI history. Do not hide durable project configuration in `workspaceState`.
- Store project paths as normalized workspace-relative paths whenever practical. Treat migration from legacy keys or hidden state as an explicit compatibility task; do not silently copy machine-specific values into a tracked project file.

## Codegen rules version (mandatory)

- `@codegen-rules-version` is the generated-code rules version, independent of the extension version, Wing package versions, legacy JSON version and Plan/cache schema. The independent series starts at `1.0.0`; current rules are `1.0.2`. Do not reuse the old Windows App `@version` number or year.
- For the same inputs, any change to generated content within a START/END control region requires a rules-version bump: generated API/signal calls, declarations/defaults, templates, emitted comments, whitespace/indentation, and start/end/clang-format boundary output. Parser/selection changes affecting which content is generated or replaced also require invalidating old plans. Pure UI, toolbars, scrolling, paths displayed only in UI, and packaging changes do not bump rules version.
- For a rules change, update the Wing exported rules constant and Auto preflight cache version together; keep the local runtime consistency gate and runtime-identity isolation. Add a regression for the changed output and rejection of the preceding cache version, update the example cache and version documentation, then run the local Wing build gate. Never change legacy golden fixtures wholesale to hide unrelated regressions, or let an old/unversioned Registry runtime claim the new rules.
- Compatible fixes increment patch, compatible new rules increment minor, and breaking generation-contract changes increment major. Do not bulk-rewrite user source just to update annotations; changes appear only on later explicit generation/apply.
- The user authorized the constructor END/clang-format fix on 2026-09-10. Rules `1.0.1` align the two closing markers to the next nonblank, non-comment-only semantic source line; when there is none, preserve the existing END indentation. Do not modify user code outside the region or format the project incidentally. Native formatter regression does not establish Windows acceptance. See [Codegen生成规则版本](docs/codegen-plan/Codegen生成规则版本.md) and [bug record](docs/bug/自动代码-构造函数结束标记缩进.md).
- The user authorized the CAA Combo update comment fix on 2026-09-10. Rules `1.0.2` emit each supported `int` / `double` / `CATUnicodeString` Combo's own `id,paramString,notes` immediately before its `UPDATE DIALOG` assignment. Keep `SetSelect` / `SetField`, unsupported cases and `UPDATE INFORS` unchanged; reject `1.0.1` plans even if other inputs are unchanged. Pure renderer tests do not establish Windows/CAA runtime acceptance. See [Combo bug record](docs/bug/自动代码-Combo参数回填缺少注释行.md).
