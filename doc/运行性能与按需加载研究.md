# 运行性能、Git 按需加载与 Codegen 刷新研究

状态：implemented（Auto 已接入 Registry Wing 0.6.0 轻量 Git API）

Owner：KT Auto Code maintainers

适用版本：0.6.x 后续迭代

研究与实现日期：2026-07-29

本文记录 KT Auto Code 的运行内存点检方法、Git Primary Block 首次加载缓慢的根因，以及 Codegen JSON 外部修改后仍显示旧内容的问题，并保存 2026-07-29 的实现边界与验证回执。

## 1. 结论摘要

1. 普通 Primary Block 共用一个 Sidebar Webview，并不是每打开一个 Block 就新建一份浏览器页面；“同时打开很多 Block”不是当前最主要的内存风险。
2. 两个 Sidebar Webview 都启用了 `retainContextWhenHidden`。Codegen 每个 JSON View 还会创建一个独立、同样保留后台上下文的 `WebviewPanel`，所以同时打开很多 Codegen JSON View 才是需要重点量测的场景。
3. Git Block 每次显示都会刷新所有候选仓库；每个仓库预取 200 条提交，而界面默认只显示 20 条。Wing 当前又对每条提交串行启动一次 `git cat-file`，这是 Git 首次加载缓慢的主要原因。
4. 用户最常用的是“获得当前仓库最新一个节点的简报”，多节点简报与多节点合并使用较少。因此 Git 应按“最新简报 → 收缩的更多 commit → 合并历史”的频率分三层加载，不能用多条历史或合并所需的完整安全数据阻塞最新简报。
5. Codegen 已打开的 JSON 会长期保存在 Extension Host session 中。再次打开已有 session 时不会复读磁盘；关闭 View 只取消 active 状态，不释放 clean session。文件监听事件一旦漏掉，关闭并重开仍会显示旧内存模型。
6. 新增一个单实例、非模态的“运行诊断”页面：从 Welcome 页底部“诊断”链接或命令面板打开，可刷新、复制/保存 JSON，并跳转 VS Code 进程资源管理器。它必须区分 Extension Host 整体内存与本插件可归因的资源数量。

## 2. 当前 Webview 与内存边界

### 2.1 Primary Block 不是一 Block 一 Webview

`extension/src/extension.ts` 注册 Ribbon 和共享工具区两个独立 Sidebar WebviewView；它们由同一个 Provider 创建并都装载 panel HTML。普通 Primary Block 只在共享工具区中切换：`openToolIds` 是历史栈，任一时刻只有 `activeToolId` 对应内容显示，主要 HTML 本来就是静态存在的。因此：

- 打开 1 个或多个普通 Block，不应线性增加 WebviewPanel 数量；
- Block 自身仍可能保留 Controller 数据、列表缓存和运行任务，不能只看 DOM；
- 两个 Sidebar Webview 当前都使用 `retainContextWhenHidden: true`，侧栏隐藏后仍保留页面状态。

### 2.2 Codegen JSON View 是主要的线性增长点

`extension/src/tools/codegen/editorViewController.ts` 使用 `Map<uri, WebviewPanel>`，每份已打开 JSON 对应一个 Panel，且启用 `retainContextWhenHidden: true`。Codegen batch apply report 另有一个可复用的 Panel，也保留后台上下文。因此 1、5、10 份 Codegen JSON View 与 batch report 应分别量测；切到后台但不关闭时，DOM 与 JavaScript 上下文仍可能保留。Panel 数量不等于 OS Webview 进程数量，VS Code 可能复用 renderer；Panel 可以精确计数，进程内存仍以 Process Explorer 为准。

VS Code 官方文档明确说明，`retainContextWhenHidden` 的行为类似后台浏览器标签，会带来较高内存开销；能用 `getState/setState` 恢复的页面应优先使用状态序列化。参考 [Webview API](https://code.visualstudio.com/api/extension-guides/webview) 和 [Custom Editor API](https://code.visualstudio.com/api/extension-guides/custom-editors)。

### 2.3 什么能归因，什么不能

| 指标 | 能否归因给 KT Auto Code | 说明 |
| --- | --- | --- |
| `process.memoryUsage()` 的 RSS/heap/external | 不能精确归因 | 它是整个 Extension Host 进程，包含同一 Host 内的其他扩展 |
| VS Code Window/Renderer/Webview 进程内存 | 不能直接精确归因 | 可通过前后场景差值和禁用其他扩展做 A/B 判断 |
| 本插件 Block、Panel、session、缓存、watcher、任务数量 | 可以 | 由各 Controller 提供只读计数，不输出业务正文 |
| Git/Codegen 操作耗时 | 可以 | 在本插件操作边界打点，记录阶段耗时与最近样本 |

所以“插件占用 300 MB”不能只由一个 Extension Host 数字得出。可信结论应是：在受控场景下，记录系统进程差值，同时用插件内部资源计数解释差值。

## 3. 内存人工点检方案

### 3.1 VS Code 现有入口

- `帮助 → 打开进程资源管理器`：观察 Extension Host、Window/Renderer 和 Webview 相关进程的 CPU、内存。诊断页可以先探测内部命令 `workbench.action.openProcessExplorer` 并尽力调用，但它不是稳定公开 API；不可用时显示这条手工路径。
- 命令面板 `Developer: Show Running Extensions`：查看激活时间并为 Extension Host 录制 CPU Profile；它不是逐扩展 heap 统计器。
- 终端 `code --status`：在 VS Code 正常运行时输出一次进程快照。
- 如需排除其他插件干扰，使用独立 Extension Development Host，或执行 `Help: Start Extension Bisect` 做 A/B。

官方操作说明见 [VS Code Performance Issues](https://github.com/microsoft/vscode/wiki/performance-issues) 与 [Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)。

### 3.2 固定场景

使用同一个代表性工作区，每一步操作完成后空闲 30 秒再记录：

| 序号 | 场景 | 重点观察 |
| --- | --- | --- |
| A | 只显示 Welcome，不打开 Block | 基线 RSS、heap、空闲 CPU |
| B | 打开 1 个、再打开全部普通 Primary Block | Webview 数是否保持不变；内存是否只小幅增加并稳定 |
| C | 关闭全部普通 Block | Controller 缓存/任务是否释放；空闲 CPU 是否回零 |
| D | 依次打开 1、5、10 份 Codegen JSON View，并切到后台 | WebviewPanel、session 与内存是否线性增加 |
| E | 关闭全部 clean Codegen View | Panel 和 clean session 是否释放；内存是否明显回落 |
| F | Git 只复制最新简报、展开最近历史、进入合并预检 | 三个阶段的耗时、Git 子进程与缓存数量 |
| G | 连续执行 10 次“打开 → 关闭” | heap/session 是否单调增长，是否存在泄漏趋势 |

每组至少执行 5 次；冷启动与缓存命中分开记录。保存 p50、p95、峰值和结束后稳定值，不用一次截图下结论。

### 3.3 建议内部验收线

以下是项目自己的目标，不是 VS Code 官方限制：

- 普通 Block 打开数量增加时，不新增独立 WebviewPanel，空闲 CPU 近似 0；
- 重复打开/关闭普通 Block 后，插件内部资源计数回到基线；
- 关闭 clean Codegen View 后，对应 Panel 与 session 被释放，不能无限累积；
- dirty 或外部冲突 session 可以保留，但必须在诊断页可见并有数量上限策略；
- 10 轮开关后 heap 不持续单调增长；垃圾回收造成的短期不回落不单独判为泄漏。

## 4. “运行诊断”非模态页面

### 4.1 入口与形态

- Welcome 页底部链接：`诊断`；与帮助、文档等链接放在同一区域，不新增一个日常 Primary Block。
- 命令面板：`KT Auto Code: 打开运行诊断`。
- 使用单实例 `WebviewPanel`，在编辑器区域非模态打开；重复点击 reveal 同一页面。
- 页面右上操作：`刷新`、`复制 JSON`、`保存 JSON`、`打开进程资源管理器`、`关闭`。
- 可选地把同一份 JSON 写入 KT Auto Code Output，便于无 Webview 时收集；不得每秒自动轮询。

页面以 MiB 和数量展示，复制/保存仍输出精确 byte。默认诊断不得包含绝对路径、Git remote、commit message、JSON 草稿、源码或环境变量；仓库只输出数量和匿名序号。若以后需要“详细路径”，必须由用户临时勾选，并在复制前提示。

### 4.3 实现边界

- 诊断 Panel 自身使用 `retainContextWhenHidden: false`；隐藏后可重建轻量页面，不能让测量工具成为新的长期内存来源。
- 诊断采集器只读，不触发 Git 刷新、Codegen 扫描/读盘或 Run 探测，否则测量本身会改变结果。
- 各领域 Controller 暴露轻量 `getDiagnosticsSnapshot()`；诊断页面只汇总 DTO，不读取私有业务对象。
- 最近耗时使用有上限的环形缓冲区，例如每类 20 条；关闭页面不等于清空样本。
- 不尝试在 Webview 中伪造“本插件独占内存”；需要精确进程证据时，引导用户打开 VS Code 进程资源管理器。
- 现有 Codegen“复制运行诊断”含工作区路径、文件名和 active URI，不能直接汇入全局诊断；必须新增 counts-only、脱敏投影。禁止普通诊断生成 V8 heap snapshot、`process.report` 或强制 GC，避免卡住 Host 或泄露正文、环境和命令行。

## 5. Git 加载缓慢的根因

### 5.1 当前调用链

1. `KtcGitTool.onDidShow()` 每次 Git Block 显示时调用 `refresh()`。
2. `refresh()` 汇总工作区、VS Code Git API 与活动文件得到所有候选仓库。
3. 候选仓库通过 `Promise.all` 并发调用 `readRepository(startPath, 200)`；整个 Block 等最慢仓库完成后才得到完整状态。读取前只按 start path 去重，活动文件目录、Workspace Folder 与 VS Code Git root 指向同一仓库时，可能在解析 canonical root 之前重复完整读取。
4. UI 默认只展示 20 条；“再加载 20”只是把已经在内存中的 200 条多显示 20 条，没有向 Git 做真正分页。
5. Wing 0.5.1 当前完整读取每个仓库时，会执行 root、HEAD、分支、upstream、remote、status、commit rev-list、remote rev-list、refs 等固定命令；随后对最多 200 个 OID 串行执行 `git cat-file -p`。

因此一个候选仓库冷读约启动 `15 + commit 数` 个 Git 子进程，其中最多 200 个 `cat-file` 不是并发常驻，而是依次创建。多仓库和重复候选又会同时开始完整读取。默认界面只用前 20 条，最新简报实际只需要 1 条，这构成明显过取。

### 5.2 使用频率决定加载层次

#### P0：最新一个节点简报（最高频）

- 打开 Git 时直接读取已有的“仓库目录缓存”并立即显示分组下拉与骨架，不再每次重新发现全部仓库。
- 当前 Workspace Folder 可同步加入目录；VS Code Git API 的 repository open/close 事件用于增量更新。只有用户点击 `重新搜索仓库`，才扫描 submodule/受控嵌套候选并重建目录。
- 选择优先级为：活动编辑器所属的当前工作区仓库 → 当前工作区上次选择 → 当前工作区首个仓库 → 用户固定仓库上次选择。
- 只读取当前所选仓库，不等待其他候选仓库的完整数据。
- 最小数据仅包含 root/name、HEAD、当前 branch/upstream、可选 remote URL 和最新 1 条 commit。
- 最新 commit 作为默认选择，提供直接的 `复制最新简报`；打开 Block 本身不自动写剪贴板。
- 不读取工作区 dirty、全部 refs、remote 可达 OID、操作状态或 200 条历史。

#### 仓库目录缓存与用户级仓库

仓库“在哪里”与 commit 内容必须分开处理：

- **仓库目录缓存**只保存规范化 root、显示名、来源分组与最后可用状态，不保存 commit、status、refs 或 remote reachability；打开 Git 可直接使用。
- **commit 内容默认不做跨仓库缓存**。选中仓库后异步读取最新 1 条，切换仓库后当前显示内容随选择替换。
- 若基线证明反复折叠/切回同一仓库仍需要优化，只允许为**当前选中仓库**保留短 TTL 内容，并用 `root + HEAD OID` 校验；切换仓库或 HEAD 变化立即丢弃。不得预热或长期缓存所有仓库历史。
- 当前工作区内仓库按相对路径保存可重建的发现结果；Workspace Folder 变化、VS Code Git repository open/close 和用户点击“重新搜索仓库”会使目录失效或增量更新。
- 工作区外常用仓库由用户显式 `＋ 添加仓库`，属于机器级用户配置，建议使用可在 VS Code 设置中编辑/删除的 `ktAutoCode.git.repositories`，绝不写入工程 `.vscode/settings.json`。其中允许保存本机绝对路径，因为它明确是用户机器资源，不是团队工程属性。
- 临时访问过但未固定的工作区外目录可以只进有上限的 `globalState` 最近记录；不能悄悄晋升为永久仓库，也不能上传到项目设置。
- 目录项启动时只做轻量存在性标记；不得为了验证所有用户仓库而逐个读取 Git 历史。选中某项后才解析真实 root、HEAD 和最新 commit；失效项保留“不可用”提示及删除入口。

下拉使用分组而不是把所有仓库平铺：

1. `当前工作区`：活动仓库置顶，其余按 Workspace Folder/相对路径稳定排序；
2. `当前工作区 · 子模块/嵌套`：来自 VS Code Git API 或最近一次手动搜索；
3. `我的仓库`：用户级固定仓库；
4. 末尾固定动作：`＋ 添加仓库…`、`↻ 重新搜索仓库`、`管理用户仓库…`。

“重新搜索仓库”只重建仓库目录，不预加载每个仓库的 commit。用户仓库与当前工作区仓库指向同一真实 root 时，以当前工作区分组显示并去重。

这里的作用域与“改名”功能允许选择其他目录相似：当前工作区只是默认和优先来源，不是功能硬边界。用户通过 `＋ 添加仓库…` 选择工作区外目录后，Host 必须先用 `git rev-parse --show-toplevel` 解析并校验真实仓库根；只加入这一个根，不扫描它的父目录、兄弟目录或整块磁盘。用户可选择“仅本次使用”或“固定到我的仓库”。

工作区外仓库可以生成简报，也可以执行 commit 合并。合并仍使用同一 Wing 隔离 worktree/临时 ref 算法，但确认页必须额外显示 `工作区外仓库`、完整真实路径、当前分支和预计改写节点数。预览、执行、撤销与锁全部绑定选中 `repositoryId + canonical root`；活动编辑器或工作区变化不得在操作中途切换目标。

#### P1：更多 commit 与多条简报（次频）

- 使用一行紧凑的 `更多 commit` 小 Block，默认收缩，不在首屏铺开历史列表。
- 折叠时不读取第二条及后续历史；每次从折叠变为展开时，自动以 OID 游标追加下一条。收起后再次展开再追加一条。
- 提供两个明确的增量动作：`下一条` 每次只再取 1 条，适合顺序查看；`下 5 条` 一次追加 5 条，适合需要多选生成简报时使用。
- 已加载行保留 checkbox，多选后一次生成多条简报；不再设置“默认加载 20、内存预取 200”的隐式批量。
- 增量查询以最后一条已加载 OID 作为游标，并携带首屏 HEAD OID；HEAD 已变化时提示刷新，避免 offset 分页造成重复或漏项。
- 当前选中仓库内相同请求合并 in-flight；如启用短 TTL，只能以 `repository root + HEAD OID` 为键。
- 切换仓库后取消或丢弃旧请求结果，不能用迟到结果覆盖当前仓库。
- 快速重复点击时同一仓库/请求类型只允许一个 in-flight；按钮等待期间禁用或把请求串行。每次提交结果前核对 generation、repositoryId 和 expected HEAD，并按 OID 去重。

#### P2：多节点合并（低频、高风险）

- 合并入口放到历史之后的“更多/高级操作”，默认折叠。
- 用户点击“选择并预检”后，才读取 clean status、操作状态、完整直线历史、refs、remote 可达性与 tag/branch 占用。
- 安全门禁不降低，只把昂贵数据从常用路径移到明确动作之后；准备时间较长时显示阶段进度和取消按钮。
- 当前 UI 以 `clean + operationState + 至少 2 条预加载历史` 决定合并入口是否启用；后续必须改为入口可展开、点击后由预检返回 blocker，不能为了决定按钮状态而在首屏读取完整安全快照。

建议最小 UI 顺序：

```text
[仓库下拉] [＋ 添加仓库]
最新 commit（始终可见，1 条）                 [生成/复制简报]
▶ 更多 commit（已加载 0）
  每次展开自动追加 1 条；展开后仍有：[下一条] [下 5 条] + checkbox 列表
▶ 合并本地 commit（高级）
  展开/点击后才读取候选与安全预检
```

### 5.3 Wing API 收敛与已实现契约

- 将完整 `readRepository` 拆为 `readRepositorySummary/readLatestCommit/readCommitPage/readRewriteSafety`，或使用显式 capabilities/options，避免布尔参数堆积。summary 返回 canonical root、HEAD、ref/upstream、最新 1 条和 `hasMore`；page 接受 `expectedHeadOid + beforeOid + limit(1|5)`，按 newest-first 返回 exclusive OID 游标。
- 提交列表改用一次可安全解析的 `git log` 格式，或 `git cat-file --batch`；不能继续为每条 commit 单独创建进程。
- summary/page 必须包含 subject/body、author、committer 与时间，保证审查 trailer 和简报完整；短 SHA 使用 Git 的仓库级唯一缩写，不能仅假设 7 位永不碰撞。
- root 确认后可以并发读取彼此独立的轻量元数据，但最大收益仍是“不读取用不到的数据”。
- UI-neutral 的分页、缓存键和安全快照类型放 Wing；VS Code Git API、活动编辑器选择和 Webview 状态留在 Auto Code Host。
- Wing Git runner 增加 `AbortSignal`。切库、手工搜索、HEAD 变化或关闭 Git 可以取消只读查询；已确认执行的 squash 事务不能因为 UI 隐藏而中断。

以上契约已由 Phoenix Wing 0.6.0 候选提交 `6311275`（`Git：增加轻量仓库摘要与OID分页`）实现：

- `pnwReadGitRepositorySummary(startPath, options)`：`maxCommits` 默认 1、范围 1..1000；可选读取 remote URL；返回 canonical root、HEAD、ref/branch/upstream 与 newest-first `PnwGitCommitSummary[]`；
- `pnwReadGitCommitPage(startPath, options)`：以必填 `expectedHeadOid` 固定浏览会话，以前一页 `nextBeforeOid` 作为 exclusive `beforeOid`；HEAD 变化或游标不可达时拒绝；
- commit 页使用一次 NUL 分隔 `git log` 批量读取，不再逐 commit 创建 `cat-file` 进程；
- summary/page 不读取 status、operation、remote reachability 与全部 refs；完整 `pnwReadGitRepository` 继续只用于 squash 安全预检；
- summary/page、兼容的完整只读链及底层 Git runner 支持 `AbortSignal`。

### 5.4 Git 验收目标

建议项目内部目标：

- 已缓存的 Git Block 再打开：≤ 100 ms 显示；
- 本地仓库冷读“最新简报”：p50 ≤ 300 ms，p95 ≤ 800 ms；
- 其他仓库不能阻塞当前仓库首屏；
- `更多 commit` 默认收缩，首次仅有已读取的最新 1 条；`下一条` 精确追加 1 条，`下 5 条` 最多追加 5 条；
- 未点击合并时，安全预检相关 status/refs/remote reachability 调用次数为 0；
- 工作区外仓库只有用户显式选择后才加入；简报和合并均使用已确认的 canonical root，合并确认明确标记外部仓库；
- 诊断 JSON 分别记录 discovery、selected summary、history page、rewrite preflight 耗时。

## 6. Codegen 外部修改不刷新的根因

### 6.1 为什么关闭再开仍旧

- `documentSessionController.open()` 发现 URI 已在 registry 中时，直接返回 existing session，不调用 `readSnapshot()`。
- JSON View 关闭时，`onDispose` 只清理问题/任务并 `deactivate(uri)`；clean session 仍在 registry 中。
- 再次打开会直接 `showSession(existing)`，因此仍显示旧内存模型。
- 关闭 Primary Block 与 JSON View session 没有生命周期关系，也不会复读磁盘。
- Primary“刷新列表”也不是内容 reload；当前重扫后 retained session 还会覆盖磁盘发现摘要，所以它同样可能继续显示旧数据。
- 文件 watcher 正常收到 changed/created 事件时能自动 reload；但 watcher 是通知机制，不应成为一致性的唯一依据。原子替换、文件提供器、排除规则或时序造成一次漏报后，当前实现没有补偿校验。
- 通过打开文件对话框选择的工作区外 JSON 不一定落在当前 workspace watcher 覆盖范围内，更需要显式打开时校验。
- View 中现有按钮只在 dirty 或 `externalConflict` 时启用。watcher 漏报时 session 仍被视为 clean、无冲突，用户看不到可用的“重新加载”。

### 6.2 P0 正确性修复

1. watcher 只作为快速提示，不作为磁盘一致性的唯一真相。新增单一 `reconcileSessionFromDisk` 流程，reopen、手工 reload 和 watcher 全部复用，并通过现有 per-URI `externalJsonEvents` 队列串行，避免读盘和 watcher 竞态。
2. show/reopen existing session 前始终复读 snapshot 并比较 fingerprint：
   - 相同：继续显示缓存，并清除已经恢复的外部冲突；
   - 磁盘变化且 session clean：自动 reload 后显示；
   - 磁盘变化且 session dirty：保留草稿、标记外部冲突并显示明确横幅；
   - 文件删除：保留内存草稿并显示 deleted 状态。
   - JSON 无效、解码失败或普通读取失败：保留最后有效模型和 checkpoint，标记 changed 并报错；不能把所有读取失败误判为 deleted。
3. 将单一 `externalConflict: boolean` 扩展为 `externalState: current | changed | deleted`，让 Host、View 与诊断能区分内容变化和删除。
4. JSON View 始终显示可用的 `重新加载`：
   - clean：先复读磁盘；内容未变化时提示“磁盘内容未变化”，发现磁盘修改时先提示并确认，再替换当前 View；
   - dirty：确认“放弃本地草稿”后复读；
   - 磁盘 JSON 无效：保留当前模型并显示错误；
   - 文件删除：不清空草稿，提示不能加载。
5. Primary 的“刷新列表”只负责发现工作区 JSON，标签和 tooltip 不得让用户误以为它会刷新已经打开的 JSON 内容。

### 6.3 P1 生命周期与内存

- 关闭 JSON View 时，仅释放 clean、`externalState === current`、View 已关闭且没有 preflight/batch/apply owner 的 session 及 payload；释放也进入同一 URI 队列。
- dirty/conflict session 继续保留，避免丢失草稿；在 Primary 和运行诊断中明确显示数量。
- 如确实需要快速重开缓存，只能使用有上限的 LRU/TTL，不能在整个 Extension Host 生命周期无限保存。
- 关闭 Primary Block 不应丢弃 JSON 草稿；它可以释放 discovery/candidate 等可重建缓存。
- 评估关闭 Codegen View 的 `retainContextWhenHidden`，改用 `getState/setState` 或 Host session 恢复轻量 UI 状态；必须先证明选择、滚动、筛选等恢复体验。
- 当前 `onDispose` 在缺少 current context 时会提前返回，可能连 deactivate/cleanup 都跳过；生命周期清理必须移到 context 判断之前，只有 UI publish 依赖 context。

### 6.4 Codegen 验收矩阵

- clean View 关闭后外部修改，再打开显示磁盘新内容；
- 模拟 watcher 漏报，再打开仍通过 fingerprint 校验刷新；
- 工作区外手选 JSON 即使不在 watcher 范围内，重开也会校验；
- clean View 随时可点“重新加载”；
- dirty + 外部修改不会静默覆盖，放弃草稿必须确认；
- 磁盘 JSON 无效或已删除时保留当前草稿并报错；
- clean View 关闭后 Panel/session 计数下降；
- dirty/conflict View 关闭后 session 仍在，诊断页数量正确；
- preflight/batch/apply 正在持有的 clean session 不会被关闭事件提前释放；
- watcher、reopen、manual reload 对同一 URI 严格串行，迟到结果不能覆盖新状态；
- 关闭/重开 Primary Block 不伪装成 JSON 内容刷新。

## 7. 推荐实施顺序

### Phase A：先建立证据

1. 新增只读运行诊断 DTO、Controller 快照和最近耗时环形缓冲。
2. 增加 Welcome/命令面板入口与单实例非模态页面。
3. 按第 3 节固定场景记录 0.6.1 基线，先确认主要增长来自 Panel、session 还是 Git 子进程。

### Phase B：Git 高频路径

1. Wing 增加轻量 summary/latest 与分页 API，消除逐 commit 子进程。
2. Auto Code 先渲染仓库选择，再只读选中仓库最新 commit。
3. `更多 commit` 改为默认收缩的小 Block，以 `下一条 / 再 5 条` 做 OID 游标增量加载；合并预检完全移出打开路径。
4. 增加冷/热、单仓/多仓、慢仓/切换取消测试与耗时验收。

### Phase C：Codegen 一致性与释放

1. existing session show/reopen 前做 fingerprint 校验。
2. 让“重新加载”在 clean 状态也可用，并覆盖 dirty/invalid/deleted 分支。
3. 关闭 clean View 时释放 session；为 dirty/conflict 保留建立明确策略与诊断计数。
4. 再评估 `retainContextWhenHidden`，以恢复体验和实测内存共同决定。

### Phase D：复测与归档

重复第 3 节全部场景，对比 0.6.1 基线。只有 Git p50/p95、Codegen 刷新矩阵和资源回收曲线均达标后，才把本文状态从 `planned` 改为 `implemented`。

## 8. 本计划明确不做

- 不把 Extension Host 整体 RSS 宣称为 KT Auto Code 独占内存；
