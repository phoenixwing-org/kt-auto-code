# KT Auto Code 0.3.0 功能计划

> 状态：规划中。`0.2.0` 已发布；`0.2.1` 只收口现有模块，首个新模块进入 `0.3.0`。本计划不承诺发布日期，按依赖顺序实施。  
> 范围：C++ 成员排序结果体验、Code 派生能力、UUID/CAA 对话框、工作集与 CAA 环境上下文。

## 1. 总体顺序

```text
CAA 环境上下文 ─┐
工作集定义 ─────┼─> Code 文件选择/结果 View ─> 成员排序、文件克隆、UUID/CAA 操作
                └─> 真实工程预检与写盘验收
```

先确定“哪些文件属于当前任务”（环境 + 工作集），再扩展“对这些文件执行什么动作”。所有写盘工具继续遵守：预检、选择、确认、写前指纹检查、Git 审核。

## 2. P0：C++ 成员排序结果 View 重构

### 目标

成员排序不再使用单一编辑器 Tab 承载长表格，而是落地 VS Code **Primary Sidebar** 中的原生结果 View，交互接近内置 Source Control / 搜索：工具页只负责触发，主侧栏结果负责浏览、筛选、预览、写盘和还原。

### 信息架构

默认按**文件名**升序展示，后续提供“按目录”树形模式；两种模式共享同一缓存快照，不重新扫描。

```text
KT Auto Code 结果 · 成员排序          [按文件名 v] [仅显示变更 ✓]

变更文件 · 待写盘 / 已写盘
  Foo.cpp                  待写盘   .cpp   [预览] [选择]
  Bar.h                    已写盘   .h     [Git Diff] [↶]

无变更文件 · 35
  Baz.h                    无变更   .h     [打开]
```

- **变更文件**与**无变更文件**分块，两个块各自显示数量、展开状态和空态。
- 默认只展开“变更文件”；“仅显示变更”关闭后才展示无变更块。
- “按文件名”是首个稳定模式，按大小写不敏感的 basename + 相对路径排序；“按目录”以相对目录建树，不改变文件状态或勾选。
- 只在用户主动点击时打开文件或 Git Diff；批量写盘后不得逐个弹出 Diff。
- 使用与 VS Code Git 接近的紧凑状态标签、文件类型标签和图标操作；操作必须有文字 tooltip 与键盘可达性，不能只依赖图标语义。
- 仍使用 VS Code 内置 Git 差异查看；不创建 `untitled` 文档、不重写 Diff 引擎。↶ 仍恢复本会话写盘前的原始字节，并拒绝覆盖外部修改。

### 结果 View 的 Git 风格约定

成员排序、UUID 与之后的多文件工具统一采用“**状态分块 → 文件优先的一行列表 → 右侧按需图标操作**”：文件名在前，目录、命中数和状态压入 description；长映射、行列和诊断放入 hover 或二级详情，不用长 token 挤占主列表。UUID 已按“待写盘 / 已写盘 / 未写入”分块；成员排序沿用“变更文件 / 无变更文件”。每个文件行至少保留打开，已写盘行按需显示 Git Diff；批量写盘不得自动弹出多个差异页。

### 技术决策与验收

1. 首选验证 `viewsContainers.activitybar` + 原生 `TreeView`，在 Primary Sidebar 呈现，不先在 Webview 中重做 Git 的列表交互。它支持分组树、多选、复选框和文件资源图标；若 API 无法满足缓存/交互，再保留编辑器 Webview 作为后备。
2. 原生列表用 `resourceUri` 获取当前文件图标主题，用 `TreeItemCheckboxState` 管理待写盘项；状态通过 `contextValue` 控制菜单和内联操作。
3. 图标只复用 VS Code Product Icon / Codicon，不复制 Git 扩展资源、不新增位图：打开原文件 `$(go-to-file)`、Git 差异 `$(compare-changes)`、还原 `$(discard)`、应用所选 `$(check)`。命令注册与 `view/item/context` 的 `inline` 分组提供与 Git 接近的行内按钮；每个图标仍有文本 tooltip、命令标题和键盘入口。
4. 当前 Webview 的 `▣ / ↶` 为临时字符。若最终仍保留 Webview，不能假设 `$(icon)` 会自动渲染；需显式引入并本地打包 `@vscode/codicons` 的 CSS/font，或改用原生 TreeView。首选后者，以自动跟随用户的 Product Icon Theme。
5. View 模型拆为 `changed`、`unchanged`、`blocked`、`applied`，排序/分组均由纯函数测试覆盖。
6. 验收：100 个以上文件时不重扫；切换文件名/目录模式不丢勾选；写盘后只更新对应行；Git Diff 和还原均为按需单文件操作。

参考：[VS Code Product Icon Reference](https://code.visualstudio.com/api/references/icons-in-labels) · [VS Code Views 指南](https://code.visualstudio.com/api/ux-guidelines/views)。

### 验证后推广原则

成员排序是原生底部结果 View 的**样板模块**。只有在真实工作区验证以下条件后，才将该模式推广给其他多文件工具：

- 大文件列表下的展开、筛选、文件名/目录切换和复选框状态稳定；
- Git Diff、打开文件、还原/应用等命令均按需执行，且键盘与屏幕阅读器可达；
- 工具切换、重载窗口和写盘后增量更新不丢失可恢复的会话状态；
- 与现有搜索替换结果和 VS Code Source Control 的用户心智一致，不增加一套自定义操作语义。

通过后提取 `Ktc` 前缀的纯结果模型、TreeDataProvider、分组/排序函数与命令注册约定，按下列优先级迁移：

1. **搜索替换**：命中/冲突/已写盘分组，沿用现有预览和确认语义；
2. **编码修正与头文件 ASCII**：问题/可修复/已修复分组，文件项直接打开定位；
3. **文件克隆与改名**：可创建/冲突/已创建分组，保留源→目标路径摘要；
4. **UUID 扫描与替换**：命中/跳过/已替换分组，映射表作为只读子节点；
5. **CAA 对话框**：只读索引与诊断优先，复杂编辑仍留在 DeskTools/Tauri。

不适合 TreeView 的复杂表单、长文本比较、分页统计和图形编辑继续使用编辑区 View；“统一结果入口”不等于强迫所有界面使用同一种控件。

## 3. P1：Code 功能盘点与两套克隆能力归位

当前已有两套克隆相关来源/计划，实施前先做一次**功能盘点**，明确每套的入口、输入、写盘语义、测试和目标用户，禁止把两个相近功能悄悄合并。

| 候选能力 | 当前定位 | 首要决策 |
| --- | --- | --- |
| 文件克隆与改名 | 保留源文件，批量生成新文件名并对副本内部做替换 | 见 [文件克隆与改名计划.md](文件克隆与改名计划.md)；作为受控模板派生 |
| 第二套已克隆 Code 能力 | 待盘点其真实来源与边界 | 明确是“复制/派生”、还是“重命名/移动”、还是 CAA 专项生成，避免与前者重复 |

盘点输出必须包含：唯一功能名、归属目录、复用的扫描/编码/工作集服务、结果 View、写盘/回滚语义、fixture 和是否作为 `0.3.0` 新模块发布。未完成盘点前不把两套 UI 同时暴露给用户。

## 4. P2：UUID 替换与 CAA 对话框

### UUID 替换

当前基础实现已经覆盖：虚线 UUID、32 位 GUID 与 Desk Tools 对齐的 CAA nested / flat brace / flat run GUID 扫描；UTF-8 / UTF-8 BOM / GBK 保持；一次会话内稳定的“同值 → 同新值”映射；可序列化的 Wing 替换计划；原生底部结果 View 的映射组/逐命中复选框、确认写盘、写前字节指纹检查、写后缓存增量状态和按需 Git Diff。32 位 GUID 写回时保持紧凑格式与原有大小写，CAA GUID 保持其原有布局。写盘后只刷新 Git，不自动打开多个 Diff。

后续要与 Desk Tools 的完整能力对齐，但不可静默扩大首版范围：

1. 加入 `fresh_per_hit` 的用户可选策略，并在 View 中清晰标明它会打破“同值同替换”的引用关系；
2. 按需导出映射审计文件（DTO 已具备，写 `.phoenix/reports` 仍由宿主决定）；
3. 每次格式扩展均以 Desk Tools UUID fixture 为对照，纯识别/格式化/计划函数继续迁入 phoenix-wing。

### CAA 对话框

CAA `.CATDlg` 的解析、IR、emit、patch 与校验优先归属 `phoenix-wing/catdlg-core`；插件只提供工作区定位、只读摘要与外部编辑器调用入口。复杂画布、属性编辑和多文件图形交互保留 DeskTools/Tauri，不复制到 Webview。

当前插件 P0 已实现 `.CATDlg` 扫描和 Git 风格文件列表；每个文件可按用户点击交由 VS Code 打开或已配置的外部编辑器打开。外部编辑器 command/args 属于插件配置，保留在 VS Code Settings；全局工程环境变量改由独立“工程环境”Block 直接读取和维护操作系统用户环境。版本化的纯数据交接 `phoenix-desk-tools.caa-dialog.v1` 继续保留给未来 bridge；完整字段、信任边界和后续 bridge 见 [CAA 对话框 Desk Tools 交接契约](CAA对话框-DeskTools交接契约.md)。

UUID 与 CAA 的共同前提是工作集：两者都必须能明确解释“本次处理了哪些文件、为什么”。

## 5. P3：工作集定义

工作集是可命名、可复现的**文件选择规则**，不是文件内容缓存，也不是全局机器偏好。

建议保存为 `<workspace>/.phoenix/worksets.json`：

```json
{
  "version": 1,
  "worksets": [
    {
      "id": "alarm-clock-ui",
      "label": "KtAlarmClock UI",
      "roots": ["KtAlarmClockUI"],
      "include": ["**/*.{h,hpp,hh,cc,cpp,cxx,CATDlg}"],
      "exclude": ["**/{build,out,node_modules,.git}/**"]
    }
  ]
}
```

- `id` 在工作区内稳定且唯一；`label` 可改。
- `roots`、`include`、`exclude` 均相对工作区，解析后必须验证路径不越界。
- 展开结果是一次运行的文件快照；工具不能在写盘阶段重新按规则静默扩大范围。
- 成员排序、克隆、UUID、CAA 对话框共用同一个解析服务；各自仍有文件类型过滤。
- 第一阶段只支持手工 JSON 与只读选择；Wing 已有 JSON 结构与工作区相对路径校验、插件已有只读加载 adapter。之后再提供编辑 UI、最近工作集和从 Git/项目文件推导建议。

## 6. P4：CAA 环境变量上下文

事实来源：[PNXCaaStudy README](../../PNXCaaStudy/README.md) 的“环境变量设定”。它要求先由 Windows 的 `tools\baseEnv.bat` 或等价的 macOS 环境配置设置变量；插件**不执行** `.bat`、shell profile 或外部脚本。

### 首期内在值

工程环境 Block 从操作系统环境读取并规范化以下四个值：

| 内部字段 | 环境变量 | 用途 | 是否必填 |
| --- | --- | --- |
| `customRoot` | `ROOT_DIR` | 自定义库根目录 | 是 |
| `thirdPartyRoot` | `ROOT_DIR_3rdParty` | 三方库根目录 | 是 |
| `coreRoot` | `ROOT_DIR_CORE` | core 根目录 | 是 |
| `caaMkVersion` | `CAA_MK_VERSION` | CAA MK 版本，例如 `19` | 否，附加值 |

### 环境值状态与操作

环境面板按每个值显示来源、状态和一个明确操作：

| 状态 | 说明 | 操作 |
| --- | --- | --- |
| 未设定 | 操作系统用户/机器环境均无值 | 显示“新建”；`CAA_MK_VERSION` 预填 `19`，根目录可选择目录或文件。 |
| 已设定 | 当前用户、机器或进程环境存在值 | 显示“修改”；保存时只修改当前用户环境，不修改机器级环境。 |
| 路径不存在 | 根目录值存在但当前机器无法访问 | 显示警告，仍可“修改”。 |

工程环境变量不属于 VS Code 插件设置。Windows 下 Block 读取当前用户/机器注册表，可持久修改或清除当前用户值，并同步当前扩展宿主；机器级值永不改写。macOS 下使用 `launchctl` 管理当前登录会话并明确其跨重启限制。插件配置（外部编辑器、范围、界面样式等）继续使用 VS Code Settings。

### 跨平台约束

- Windows 优先刷新注册表中的当前用户/机器值，解决 VS Code 主进程未重启造成的 `process.env` 陈旧问题；进程专用值仍可作为回退。
- 不解析或执行 `tools\baseEnv.bat`；该脚本只是用户设置环境的参考来源，不能成为插件的隐式副作用。
- 每个值显示为“未设置 / 已设置但路径不存在 / 可用”；不得在日志或遥测中泄露非必要的完整路径。
- Block 内修改后当前扩展宿主立即使用新值；新终端和其他应用仍需重新启动后继承。不得重新增加同名 VS Code Settings 覆盖。

## 7. 验收与版本节奏

版本号遵守以下规则：

- **新增用户可见模块/工具**：次版本加 `0.1`，例如 `0.2.0 → 0.3.0`。
- **现有模块内的 UI、算法、兼容性或修复**：补丁版本加 `0.01`，例如 `0.2.0 → 0.2.1`。
- 仅文档、构建或发布资料变更不单独触发 Marketplace 版本；与下一次功能发布合并。

| 阶段 | 最小验收 | 建议版本 |
| --- | --- | --- |
| P0 成员排序 Panel | 分组/排序、按需 Git、100+ 文件缓存不丢状态 | 0.2.1 |
| P3 工作集 + P4 环境 | JSON 工作集可解析；三项必填根目录与附加 MK 版本可读/可覆盖 | 0.2.1 或 0.2.2 |
| P1 克隆盘点 | 两套能力边界与唯一命名明确 | 不单独发版 |
| P1 首个克隆模块 | 受控预览、写盘、fixture 与真实工程验收 | 0.3.0 |
| P2 UUID/CAA | 只读扫描与 fixture；无未审阅写盘 | 后续新模块，各升 0.1 |

每个阶段完成后必须记录：自动测试、真实工作区只读/写盘验收、Git 审核结果和未覆盖边界；不以“界面可打开”作为完成标准。
