# KT Auto Code 项目调查

> 调查时间：2026-07-11
> 调查范围：根目录 README、`doc/`、核心源码、CLI、VS Code 扩展和测试。

## 结论

KT Auto Code 是一套面向 **CAA / MSVC C++** 工作流的源码编码治理工具。它针对中文 Windows（CP936 / GBK）与跨国协作中常见的代码页差异，扫描并修正可能引发 **MSVC C4819**、乱码或跨平台解释不一致的文件。

项目当前不是纯规划或原型：两个核心工具、CLI、VS Code / Cursor 扩展入口和自动化测试均已落地。它更接近一个可用的内部工具初版，当前发布候选版本为 `0.2.0`，仓库标记为 `private`。

## 解决的问题

CAA 工程的历史工具链经常依赖本机代码页。头文件中一旦混入 Word / PDF 粘贴产生的 Windows-1252 弯引号、NBSP、全角标点、GBK 中文或 BOM，同一批字节在不同国家和不同系统代码页上可能得到不同解释。

项目将问题拆成两个层次：

| 工具 | 处理层次 | 当前能力 | 默认目标 |
| --- | --- | --- | --- |
| `headerAscii` | 文件内容的字节级清理 | 识别并替换 CP1252 标点、NBSP、全角标点及其他非 ASCII 内容；识别 BOM | 头文件保持纯 ASCII |
| `encodingFix` | 整个文件的编码检测与转换 | 识别 ASCII、GBK、UTF-8、UTF-8 BOM、UTF-16、UTF-32 和未知编码 | UTF-8 无 BOM |

两者不是重复功能：`encodingFix` 回答“整个文件是什么编码、是否需要转码”，`headerAscii` 回答“文件内容中有哪些不应出现的字节或字符”。

字符映射、扫描扩展名和 BOM 行为的完整规则不在本文重复，分别以[源文件编码扫描](./源文件编码扫描.md)和[编码修正](./编码修正.md)为准。

## 实际使用形态

项目提供两套入口，共用同一份核心逻辑：

```text
CLI scripts ─────┐
                 ├──> src 核心扫描/转换 ──> 目标工程文件
VS Code 扩展 ────┘
```

### CLI

- `scan-encoding`：扫描源文件中的问题字节。
- `fix-headers`：将头文件清理为纯 ASCII，会写回文件。
- `scan-file-encoding`：预检整文件编码。
- `convert-file-encoding`：将可转换文件写为 UTF-8 无 BOM。

CLI 的完整参数和示例见[源文件编码扫描](./源文件编码扫描.md)与[编码修正](./编码修正.md)。

### VS Code / Cursor 扩展

扩展在 Activity Bar 提供一个 **KT Auto Code** 入口，简单版 Side Bar 内注册四个工具选项卡：

- **头文件 ASCII 修正**：预检、修复、问题定位、是否保留 GBK 中文、是否去除 BOM。
- **编码修正**：编码预检、转换确认、结果定位和详细检测信息。

扩展只负责工作区、交互、确认框、结果展示和打开文件；扫描与转换仍调用根目录 `src/`，因此 CLI 与插件没有两套独立算法。

## 代码结构与职责

| 目录 | 职责 |
| --- | --- |
| `src/` | 无 VS Code 依赖的核心扫描、BOM、转码、范围和 ignore 逻辑 |
| `scripts/` | CLI 参数解析与报告输出 |
| `extension/` | VS Code / Cursor 扩展、Webview Side Bar 和命令注册 |
| `tests/fixtures/` | GBK、UTF-8 BOM、UTF-16、弯引号等回归样例 |
| `doc/` | 产品约束、详细规则、插件设计和开发说明 |

核心实现分工如下：

- `sourceEncodingScan.ts` / `sourceEncodingWalk.ts`：字节级扫描、ASCII 清理和目录遍历。
- `fileEncoding.ts` / `fileEncodingWalk.ts`：整文件编码检测、期望判断和 UTF-8 无 BOM 转换。
- `fileBom.ts`：BOM 识别及 UTF-16 等文件的安全转换。
- `scanScope.ts`：头文件、源文件、Markdown 范围及默认跳过目录。
- `dotIgnore.ts`：读取 `.phoenix/.ignore`，也支持从 `.gitignore` 同步规则。
- `extension/src/tools/`：工具注册表及 `headerAscii`、`encodingFix` 的插件适配层。

## 行为边界与注意事项

1. 这是编码和字节治理工具，不理解 C++ 语法。它不会判断被替换的中文是否位于注释、字符串字面量或其他语义位置。
2. `fix-headers` 和编码转换会直接写回目标文件。插件提供确认框，CLI 调用者仍应先预检，并通过 Git diff 审查结果。
3. GBK 检测采用“UTF-8 严格解码失败后，字节流符合 GBK 双字节规则”的策略；它适合目标场景，但不是通用的编码概率识别器。
4. UTF-32 和未知编码当前仅报告，不自动转换。
5. ASCII 同时也是合法的 UTF-8 无 BOM，因此整文件编码工具会把纯 ASCII 判为符合目标。
6. 扫描会跳过常见构建目录和隐藏目录；工作区还可用 `.phoenix/.ignore` 缩小范围。
