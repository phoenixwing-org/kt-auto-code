# KT Auto Code 代码规范

> 适用范围：根目录 `src/`、CLI、`extension/` 和后续 Vue Webview。
> 前端构建、依赖和主题规则见 [前端开发规则](./前端开发规则.md)。

## 1. 命名与前缀

KT Auto Code 不是通用 npm 组件库，但仍以命名空间优先：凡是跨文件、跨层、可复用或可能进入共享运行时的名称，默认带 `Ktc` / `ktc` / `KTC_` 前缀。只在短生命周期的局部变量、参数、对象字段和循环索引上保留自然领域名称。

| 范围 | 规则 | 示例 |
| --- | --- | --- |
| 产品显示名 | `KT Auto Code` | Activity Bar、标题、文档标题 |
| npm / 文件夹 / View Container | `kt-auto-code` | `kt-auto-code`、`kt-auto-code.svg` |
| VS Code 命令、配置、View ID | `ktAutoCode` | `ktAutoCode.searchReplace.open` |
| 跨文件 TypeScript 类型/类 | `Ktc` + PascalCase | `KtcTool`, `KtcSearchReplaceRequest`, `KtcReplacementRule` |
| 跨文件函数 | `ktc` + camelCase | `ktcResolveReplacementRules()`, `ktcCreateNonce()` |
| 模块级常量 | `KTC_` + UPPER_SNAKE | `KTC_PROFILE_VERSION`, `KTC_CAA_REPLACEMENT_RULES` |
| Webview CSS / `data-*` / CSS 变量 | `ktc-` / `--ktc-` | `.ktc-rule-row`, `--ktc-row-gap` |
| 工作区配置文件 | `.phoenix/` | `.phoenix/.ignore`, `.phoenix/search-replace.json` |

### 1.1 `Ktc`、`KTC` 与 `KT Code`

- TypeScript 中使用 **`Ktc`**，例如 `KtcTool`，不写 `KTCTool`。这与 phoenix-wing 使用 `Pnw` 的做法一致，也符合 PascalCase 可读性。
- 常量使用 **`KTC_`**，例如 `KTC_PROFILE_VERSION`。
- 品牌和用户界面仍完整写 **KT Auto Code**。
- **不使用 `KT Code` 作为新的技术前缀或产品别名**：语义过宽，且易与代码编辑器、用户项目名称混淆。
- `src/` 的导出类型、函数和模块级常量同样默认带前缀，例如 `KtcReplacementRule`、`ktcRunWorkspaceRename`、`KTC_CAA_REPLACEMENT_RULES`；这样 CLI、插件、Desk Tools 或未来共享包不会互相污染。
- 函数参数、短变量、内部对象字段仍写 `rule`、`entry`、`report`、`root` 等领域名称。不要写 `ktcRule`、`ktcEntry` 造成噪音。

### 1.2 迁移原则

- 新代码从第一行遵守上述规则；已有跨文件符号在所属 feature 重构时成组迁移，避免一次全仓库无行为改名。
- 现有 `KtTool`、`ToolRunContext`、`ReplacementRule`、`runWorkspaceRename` 等在下一次触及共享 contract / 搜索替换重构时统一迁移为 `KtcTool`、`KtcToolRunContext`、`KtcReplacementRule`、`ktcRunWorkspaceRename`。本仓库内部没有外部兼容负担时，同提交改完所有引用，不保留无意义别名。
- `codeRenameTool` 这类模块内实例可以保留自然 camelCase；对外注册 ID 才使用 `ktAutoCode.*`。
- 模块级 `CAA_REPLACEMENT_RULES` 也按规则迁移为 `KTC_CAA_REPLACEMENT_RULES`；局部规则数组则保持 `rules`。

## 2. 分层与依赖方向

依赖只能从外层指向内层：

```text
Webview View  ->  Extension Controller  ->  src/ 应用/领域服务
                                  ->  VS Code / 文件系统适配器
```

| 层 | 目录建议 | 可以做什么 | 禁止做什么 |
| --- | --- | --- | --- |
| 领域算法 | `src/` | 规则解析、编码检测、字节替换、结果汇总 | 导入 `vscode`、DOM、Webview 消息、弹窗 |
| 应用服务 | `src/` 或 `extension/src/<feature>/` | 扫描/预览/写盘计划、组合领域函数 | 拼接 HTML、直接操纵 DOM |
| Extension Controller | `extension/src/<feature>/` | 校验 DTO、读取工作区、确认框、日志、调用服务 | 内联大段 HTML、实现字节算法 |
| Repository / Adapter | `extension/src/<feature>/` | `.phoenix` 配置、`WorkspaceEdit`、VS Code 状态 | 混入 View 状态或渲染文案 |
| View / ViewModel | `extension/src/sidebar/`、`extension/src/workbench/` | 事件收集、展示、局部筛选和分页 | 文件读写、命名派生、业务冲突决策 |

### 2.1 搜索替换的目标结构

```text
src/
  replacementRules.ts                  # 纯规则校验、派生和匹配
  workspaceRename.ts                   # 扫描、预览/写盘计划
  searchReplaceContracts.ts            # KtcSearchReplaceRequest 等 DTO
  searchReplaceProfiles.ts             # 规则档案模型
  searchReplaceProfileRepository.ts    # .phoenix/search-replace.json
extension/src/
  searchReplaceController.ts           # VS Code 确认、日志、服务调用
  searchReplaceProfileController.ts    # 档案选择、更新/另存确认
extension/src/workbench/
  codeRenamePanel.ts                   # Panel 生命周期、消息转发、渲染
```

- `CodeRenamePanel` 不再拥有“执行搜索替换”的业务入口；Side Bar、命令和 Panel 都调用同一 Controller。
- `searchReplaceContracts.ts` 是搜索请求 DTO 的唯一来源；不得在 Panel、Tool 和 HTML 各复制一份请求类型。
- View 只展示 `RenameResultViewModel`。Source、Target/位置、源地址和状态文本由 ViewModel 生成并可单测。

## 3. 重复代码与函数整理

### 必须提取的情形

- 两处以上重复的同一业务判断、路径显示、错误转换、消息 DTO 或规则派生。
- 需要用注释才能解释的循环、分支或字符串拼接。
- 可独立测试的输入/输出逻辑，例如规则竞争、行号摘要、路径缩略、预设 marker 合并。
- 同时被 CLI、Side Bar、Workbench 或未来 Desk Tools 使用的逻辑。

### 不应提取的情形

- 只在一处出现且三五行即可理解的局部组装。
- 为了一行调用而创建没有领域名称的 `helpers.ts`、`common.ts`、`utils.ts`。
- 仅用于绕过 TypeScript 类型而存在的 `any` 包装函数。

### 命名和形状

- 动词开头：`resolveReplacementRules`、`buildRenameResultViewModel`、`loadSearchReplaceProfiles`。
- 布尔：`is` / `has` / `can` / `should` 开头；不要用含糊的 `check`、`flag`。
- 转换：`toXxx`、`fromXxx`、`parseXxx`、`formatXxx`；`format` 只用于人可读文本，不能隐藏写盘或网络副作用。
- 创建：`createXxx`；缓存读取：`loadXxx`；写入：`saveXxx`；更新已存在对象：`updateXxx`。
- 参数使用对象承载三项及以上、或含可选项的输入；输出使用明确的 `Result` / `Report` / `ViewModel`，不返回位置含义不清的元组。
- 纯函数不修改传入数组/对象；需要排序时复制后再排序，或在名称中明确 `sort...InPlace`。

## 4. UI、消息与状态

- Webview 到 Host、Host 到 Webview 的消息必须定义在共享 contract，并在 Controller 做运行时校验。
- Webview state 只保存草稿、Tab、筛选、展开、分页等可丢失的界面状态。
- 工作区可共享配置只由 Repository 读写 `.phoenix/`；机器级 `globalState` 只允许保存用户明确开启的非敏感便利设置。
- 不在 HTML 模板中计算规则、扫描文件、拆完整路径或决定冲突；这些放在 Host 的 ViewModel/Controller。
- UI 文案集中在 feature 的 `labels.ts` 或 ViewModel；不得把同一中文提示散落在多个事件分支。
- Side Bar 使用 `ktc-` CSS 类和 `--ktc-` 变量；未来 Vue 组件必须使用 `<style scoped>`，但仍保留前缀以避免动态类名冲突。

## 5. TypeScript、文件与测试

- 使用 ESM / NodeNext 规则；跨 `.ts` 源文件导入一律写 `.js` 后缀。
- `src/` 不得导入 `vscode`、Vue、Element Plus 或 Webview API；`extension/` 可依赖 VS Code，但不得将其类型泄露到核心算法 API。
- 不使用 `any`；边界未知数据用 `unknown` 后收窄。可选字段要表达“缺失”与“空字符串”的区别。
- 文件名采用领域 kebab/camel 的既有目录风格；一个文件一个主职责，不建立无边界的 `utils` 目录。
- 新增/修正纯逻辑时补 Vitest；测试覆盖正常、空输入、冲突、边界编码和写盘前后一致性。
- UI 改动至少做 TypeScript 构建和 Extension Host 冒烟；大结果、窄 Side Bar、浅/深/高对比主题属于 UI 验收。

## 6. 提交前清单

- [ ] 新增跨文件名称符合 `Ktc` / `ktc` / `KTC_` / `ktc-` 规则；局部参数和字段保持自然领域名。
- [ ] 新业务逻辑没有写进 HTML、Vue 组件或 Panel 渲染函数。
- [ ] 没有重复定义 Webview message、请求 DTO 或路径展示规则。
- [ ] 纯函数有聚焦单测；写盘行为先有预览和冲突保护。
- [ ] 用户文案符合“`UTF-8` 默认无 BOM；`GBK → UTF-8`”约定。
- [ ] 运行 `pnpm test`、根 TypeScript 检查、`pnpm -C extension build`；涉及 VSIX 时再运行打包。
