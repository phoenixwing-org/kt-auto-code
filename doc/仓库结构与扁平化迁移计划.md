# 仓库结构与扁平化迁移计划

状态：current

Owner：KT Auto Code maintainers

适用版本：0.6.3+

最后核验：2026-08-08

## 结论

`extension/` **当前仍在使用，不是废弃目录**。它是 pnpm workspace 中唯一的扩展包，也是以下运行链路的实际根目录：

- `extension/package.json`：`kuntai.kt-auto-code` Marketplace manifest；
- `extension/src/`：VS Code Extension Host、Primary/Webview 与各功能 Host adapter；
- `extension/media/`、`extension/resources/`：扩展图标和随 VSIX 发布的只读 runner；
- `extension/dist/`：esbuild 生成、被 VSIX 收入的运行 bundle；
- 根 `.vscode/launch.json`：以 `${workspaceFolder}/extension` 作为 `extensionDevelopmentPath`；
- 根 `package.json`：通过 `pnpm -C extension` 执行类型检查、构建和打包。

此前已经完成的是 **KT Auto CAD 从仓内 `extensions/kt-auto-cad` 迁往并列仓库**。Auto Code 自身的 `extension/` 上移只经过讨论，尚未实施。

## 当前结构

```text
package.json          # 私有编排包：开发、测试、Wing 门禁和发布命令
pnpm-workspace.yaml   # 当前只有 extension 一个 workspace package
src/                  # 无 vscode 依赖的 Auto 领域模型、工作流和算法
extension/            # 当前有效的 KT Auto Code VS Code 扩展包根
scripts/              # CLI + 开发/构建/测试/打包/发布门禁
tests/fixtures/       # 根算法、CLI 与 Extension Host 代表夹具
doc/                  # 当前文档、专项计划和历史归档
dist/vsix/            # Git ignored 的正式 VSIX 与 SHA-256
```

`src/` 不是所有跨产品核心能力的总库。真正跨宿主、跨产品共享的算法与契约以 Phoenix Wing 为真源；根 `src/` 只保留 Auto Code 自身仍需复用的 Host-neutral 模型、工作流和兼容算法。

## 为什么仍建议扁平化

CAD 拆仓后，本仓只发布一个 VS Code 扩展，继续保留“根编排包 + 唯一 extension 子包”会产生重复版本、两份 package manifest、`pnpm -C extension` 转发和两个 dist 概念。让仓库根直接成为扩展包可减少发布路径和 AI/人工理解成本。

扁平化不是删除 `extension/` 后改几条文档。它会同时影响源码导入、workspace、F5、esbuild、VSCE、资源路径、制品门禁和发布 worktree，因此必须独立实施和验证。

## 推荐目标结构

```text
package.json          # 根即 kuntai.kt-auto-code 扩展 manifest，并保留开发/发布命令
src/
  core/               # 由当前根 src/ 迁入的 Host-neutral Auto 逻辑
  extension/          # 由当前 extension/src/ 迁入的 VS Code Host 与 Webview
media/                # Marketplace 与 Activity Bar 图标
resources/            # 随 VSIX 发布的只读 runner
scripts/              # CLI、开发、验证和发布脚本
tests/
  fixtures/           # 统一根夹具
  webview/            # 当前 extension/test-fixtures 的浏览器夹具
doc/
dist/
  extension.js        # 扩展运行 bundle
  vsix/               # 正式 VSIX 与 SHA-256
```

目录名称以实施时的小型验证为准，但必须满足：仓库根是唯一 package/版本真源；根 `src/` 不导入 `vscode` 的边界继续由架构门禁证明；Extension Host 与 Webview 代码有明确子目录，不能与领域算法重新混成一层。

## 实施步骤

1. 冻结当前 0.6.3 基线：`pnpm verify:ci`、本地 Wing `pnpm ext:dev:code:prepare`、F5 和 VSIX 文件清单。
2. 合并根与 `extension/package.json`：保留根开发/门禁脚本，迁入 Marketplace manifest、VS Code engines、contributes、dependencies 与 `main`。
3. 将根 `src/` 和 `extension/src/` 分别迁入目标分层，机械修正导入；不得借机改业务行为。
4. 上移 `media/`、`resources/`，合并测试夹具，并调整 esbuild、launch、Host smoke、VSCE ignore 与制品检查路径。
5. 删除只剩转发作用的 pnpm workspace 和 `pnpm -C extension` 命令；版本只在根 manifest 维护一次。
6. 依次验证单测、typecheck、architecture、Registry build、本地 Wing build、Extension Host smoke、VSIX 内容和 SHA-256。
7. 单独中文提交；不与 Wing 升级、功能开发或 Marketplace 发布混合。

## 硬性验收

- 仓库根 `package.json` 是唯一扩展 manifest 与版本真源；
- 不再存在运行所需的 `extension/` 目录，也不保留兼容复制；
- `src/core` 或等价目录无 `vscode`、DOM 和 Webview 依赖；
- `pnpm dev`、F5、`pnpm package` 与 `pnpm verify:ci` 均从根工作；
- VSIX 的扩展 ID、命令、设置、图标、LICENSE/NOTICE 和运行资源与迁移前一致；
- 正式依赖仍来自 npm Registry，lockfile 不出现 `link:`、`file:`、workspace override 或本地 Wing 路径；
- 扁平化前后 VSIX 代表功能与 Extension Host smoke 行为一致。

在上述迁移真正完成前，任何当前文档和脚本都必须继续把 `extension/` 当作有效目录，不能提前删除或改成已扁平化状态。
