# 前端开发规则

> 适用范围：KT Auto Code 的 VS Code / Cursor 插件界面。
> 架构规划见 [VS Code 插件规划](./vscode插件规划.md)。
> Side Bar 功能拆分见 [Side Bar 界面改进计划](./侧边栏界面改进计划.md)。

## 1. 技术组合

本项目采用以下固定组合：

```text
Extension Host：TypeScript + VS Code API，不引入 Vue / Pinia / Element Plus
Side Bar：Vue 3 + 轻量 phoenix-wing 组件
Workbench：Vue 3 + phoenix-wing，按需使用少量 Element Plus
```

Side Bar 在同一 View Container 下贡献多个 VS Code 原生可伸缩 View：工具、属性、结果、任务与日志。复杂结果、批量操作、差异预览、日志及工作台放入编辑区的 `WebviewPanel`。

## 2. 运行时边界

### 必须

- Extension Host 负责文件系统、扫描、转换、确认框、VS Code 配置和跨视图状态。
- Vue 只运行在 Webview，不得在 `extension.ts`、Controller、Model 或核心 `src/` 中使用。
- Side Bar 与 Workbench 必须通过消息协议调用 Controller，不得直接导入根目录扫描实现。
- 跨 Webview 边界的数据必须可以被结构化克隆，不传递函数、Vue Ref、DOM 节点或类实例。

### 禁止

- 禁止在 Extension Host 中导入 `vue`、`pinia`、`element-plus` 或 `phoenix-wing` 的 Vue 根入口。
- 禁止让 Webview 直接读写工作区文件或 VS Code 配置。
- 禁止让 Side Bar 和 Workbench 各自维护独立的任务真相。

## 3. 状态规则

- Extension Host 的 `ToolStateStore` 是扫描任务、转换状态、结果和配置的唯一权威来源。
- Pinia 仅管理 View 本地状态，例如筛选、排序、展开、选中行、列宽和当前标签。
- Host 状态变化必须广播到所有已打开 View；后打开的 View 必须能取得完整快照。
- 关闭并重新打开 Workbench 后，Host 中仍在运行或已完成的任务不得丢失。
- 消息类型集中定义并进行运行时校验，不在组件内随意拼接消息对象。

## 4. Vue 与组件规则

- Side Bar 的工具块和属性块使用同一份 Vue 3 bundle，通过 `viewKind` 选择根组件；Workbench 使用独立 Vue 入口。
- Side Bar 的结果和任务块优先使用原生 `TreeView`，不得仅为树形列表启动新的 Vue Webview。
- Vue `WebviewView` Block 原则上不超过两个；新增 Block 优先选择原生 TreeView。
- 组件只负责展示与收集交互；业务编排放 Controller，领域算法放根目录 `src/`。
- Side Bar 组件必须适合窄宽度，不引入 Ribbon、大型表格或多栏工作台。
- 工具切换器允许使用迷你 Ribbon：默认大图标 stacked 布局，极窄宽度自动换为 2×2；用户可通过 `ktAutoCode.sidebar.toolPickerStyle` 切换为 compact。
- `phoenix-wing` 组件按具体文件或稳定子入口导入，不从混合根入口无差别导入。
- `phoenix-wing` 的属性 Schema 可用于 Side Bar，但配置写入必须经过 Controller。
- Workbench 可使用 `PnwPageHeader`、Workbench Tab、日志、进度浮层和可调表格等复杂组件。

## 5. Element Plus 规则

Element Plus 是可选依赖，只用于 Workbench 中确有价值的复杂控件。

### 必须

- 按组件导入，仅打包实际使用的组件与样式。
- 优先使用 VS Code 原生交互、HTML 控件和 CSS variables。
- Element Plus 样式必须适配 VS Code 主题变量，并验证深色、浅色和高对比度主题。

### 禁止

- 禁止 `app.use(ElementPlus)` 全量注册。
- 禁止全量导入 `element-plus/dist/index.css`。
- 禁止仅为按钮、复选框、输入框等简单控件引入 Element Plus。
- Side Bar 默认禁止依赖 Element Plus；例外必须说明体积和交互收益。

当前 `phoenix-wing` 中直接依赖 Element Plus 的组件主要是 `PnwChoiceDialogHost` 和 `PnwAsyncProgressOverlay`。接入前必须确认它们只进入需要的 Webview bundle。

## 6. Pinia 规则

- Pinia 不是初始迁移的必选项；简单页面优先使用 Vue `ref` / `computed`。
- 只有跨多个组件共享 View 本地状态时才创建 Store。
- Pinia Store 不负责文件扫描、写盘、VS Code 配置或任务持久化真相。
- 不得把 `usePnwAsyncTaskStore` 直接作为 Host `ToolStateStore` 的替代品；若使用，只保存 Host 状态的界面投影。

## 7. 界面文案

### 编码名称

- 转码目标在界面中简写为 `UTF-8`；默认含义是 **UTF-8 无 BOM**。
- GBK 转码的用户文案统一写为 `GBK → UTF-8`。
- 只有当文件实际带 BOM，或操作专门讨论 BOM 时，才写 `UTF-8 BOM`。
- 技术日志与内部类型可保留 `utf8-bom`、`UTF-8 no BOM` 等精确值。

## 8. 构建与体积规则

- Extension Host、Side Bar 和 Workbench 分别构建，Host bundle 不得包含 Vue 或 Element Plus。
- 工具块和属性块必须加载同一份 Side Bar bundle，不得各自产生一套业务代码。
- Side Bar 与 Workbench 应复用同一份 Vue/vendor 产物，避免在 VSIX 中重复存放框架代码；不同 Webview iframe 的运行时内存仍需单独计量。
- Workbench 的大型表格、日志、进度浮层等按路由或功能动态加载。
- 生产 VSIX 不包含 source map、测试文件、示例源码和未使用资源；开发构建可以保留 source map。
- 构建必须输出 bundle 体积报告，至少记录原始大小和 gzip 大小。
- 引入新依赖或组件后必须比较体积；单次 gzip 增量超过 200 KB 时，需要在变更说明中写明原因和替代方案。
- 在形成首个 Vue 版本后记录 Side Bar、Workbench、共享 vendor 和 VSIX 的基线大小，后续 CI 按基线设置预算。

## 9. Webview 安全与资源

- 所有脚本、样式和图片通过 `webview.asWebviewUri()` 加载。
- 每个 View 使用严格 CSP 和 nonce，不允许内联可执行脚本或远程脚本。
- 不使用 `unsafe-eval`；生产构建不得依赖 eval source map。
- Side Bar 与 Workbench 共用消息协议，但使用独立 View 标识，Controller 必须校验消息来源和 payload。
- Block 的折叠、尺寸、顺序及标题工具栏由 VS Code 原生 View Container 管理，不在 Webview 内模拟，也不写入 Pinia。

## 10. 验收清单

- [ ] Extension Host bundle 不含 Vue、Pinia、Element Plus。
- [ ] Side Bar 在窄宽度下无横向溢出，未加载复杂 Workbench 组件。
- [ ] 工具、属性、结果、任务 Block 可独立折叠和调整高度；结果/任务使用原生 TreeView。
- [ ] Workbench 可在编辑区打开、复用、关闭和恢复状态。
- [ ] 左右 View 同时打开时，任务状态和结果一致。
- [ ] Element Plus 为按需导入，没有全量 CSS。
- [ ] 深色、浅色和高对比度主题可用。
- [ ] 生产构建无 source map，已生成体积报告。
- [ ] CLI 与插件调用同一份核心 API，扫描结果一致。
